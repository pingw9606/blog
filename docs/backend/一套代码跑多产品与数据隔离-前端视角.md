# 一套代码跑多产品 —— 前端视角：PRODUCT_LINE 与数据隔离

> 背景：这次项目一份后端代码要同时跑 VibeShort、StoryReel（还有老的 ShortTV），C 端也是一套代码复刻出多个站。"一套代码多产品"怎么做到互不串数据？这篇讲清 `PRODUCT_LINE`、配置隔离、库/Redis 隔离这套多产品架构。

---

## 0. 目标：一份代码，多个产品，各跑各的、互不影响

我们不想给每个产品维护一份独立代码（改个功能要改 N 遍）。目标是**一套代码**，靠"配置 + 标识"跑出多个产品，且各产品的**数据、缓存、域名完全隔离**。

## 1. 后端：靠 `PRODUCT_LINE` + Nacos 配置区分

后端一份 jar，启动时用环境变量说明"我这次是哪个产品"：
```bash
java -jar seo-web.jar -DPRODUCT_LINE=vibeshort -DNACOS_NAMESPACE=<环境命名空间> ...
```
- `PRODUCT_LINE` 决定去 Nacos 拉哪份配置：`application-vibeshort-prod.yaml` / `application-storyreel-prod.yaml`…
- 每份配置里是该产品专属的**数据库地址、Redis、密钥、CDN 域名**（见《[Nacos配置中心](./Nacos配置中心-前端视角)》）。
- 同一份代码、同一个 jar，同环境不同产品**只改 `PRODUCT_LINE`** 就跑成不同产品。

## 2. 数据隔离：每产品独立库 + 独立 Redis（关键红线）

光配置区分不够，**数据必须物理隔离**：
- **MySQL**：每个产品**独立的库**（vibeshort 一套、storyreel 一套），不能共用——否则两个产品的用户/内容混在一起。
- **Redis**：每个产品**独立实例/独立 db**，不能共用——否则缓存 key 冲突、串数据（老 shorttv 和新产品 key 撞车）。

> 这次上线 checklist 里"生产主库隔离""Redis 独立实例"是**阻塞项**（不隔离不许上线）——就是防止新产品连到别人的库/缓存。踩过的教训：预发配置一度还指向 storyreel 的库。

## 3. 多租户 vs 多实例（两种隔离思路）

- **多实例隔离**（我们主要用的）：每产品一套独立部署 + 独立库/Redis，物理隔离，最干净。
- **多租户（yudao tenant）**：同一套库用 `tenant_id` 字段逻辑隔离（一张表存多租户数据，查询自动带 tenant 过滤）。框架支持，但数据在一起，隔离性弱于多实例。
- 我们是"多产品 = 多实例 + 独立库"为主，租户机制为辅。

## 4. 前端侧：一套代码怎么变多个站

- **C 端**：`vibeshort-website` 是复刻的一套 Next 代码，品牌/域名/社交链接等统一从 `config/site.ts` 读取——**换站只改 config**，不改业务代码。
- **后台**：`xxx-seo-admin-web` 一套代码，用 `switch-config` 脚本 + `PRODUCT_LINE` 构建出不同产品的包（`build:vibeshort:prod` / `build:storyreel:prod`）。
- **埋点**：一套埋点代码，靠 HTTP header `App-Id`（VibeShort=2616、StoryReel=…）区分产线，数据落同一张表用 `server_app_id` 区分（见《[埋点全链路](./埋点全链路-前端视角)》）。

## 5. 前端会撞见的

- **"预发连到了别人的库/数据不对"**：先查该产品该环境的 Nacos 配置 + 是否连对独立库。
- **改一处要想到多产品**：一套代码改动，会影响所有产品——改公共逻辑要考虑各产品差异，别把某产品特例写死。
- **品牌/域名硬编码是坑**：新站复刻时忘了从 config 读、写死了老品牌/域名。

## 6. 一句话总结

- **一套代码多产品** = 后端 `PRODUCT_LINE` + Nacos 按产品配置；前端 `config/site.ts` + 构建切换 + 埋点 `App-Id`。
- **数据必须隔离**：每产品独立 MySQL 库 + 独立 Redis（上线红线），否则串数据。
- 前端记住：**改公共代码影响所有产品**，别硬编码品牌/域名，数据不对先查产品对应的配置和库。
