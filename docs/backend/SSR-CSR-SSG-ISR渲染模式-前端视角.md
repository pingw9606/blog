# SSR/CSR/SSG/ISR —— 前端视角：Next.js 四种渲染与"build 依赖后端"的坑

> 背景：这次项目是 Next.js（App Router）做的 SEO 站，踩了几个和渲染模式直接相关的坑：详情页 500（ISR 与读 host 冲突）、build 时预渲染调后端 403 导致构建失败、C 端 SSR 走内网取数……这篇把四种渲染模式讲清楚，以及它们在 SEO 站里的取舍和踩坑。

---

## 0. 四种渲染模式

| 模式 | 全称 | 页面 HTML 什么时候生成 | 前端类比 |
|---|---|---|---|
| **CSR** | 客户端渲染 | 浏览器里 JS 跑完才有内容 | 传统 SPA（白屏→JS 填充） |
| **SSR** | 服务端渲染 | **每次请求**在服务器实时生成 | 请求来了现做一份 HTML |
| **SSG** | 静态生成 | **构建时**就生成好静态 HTML | 提前烤好，谁来都发同一份 |
| **ISR** | 增量静态再生 | 构建时生成 + **过期后台再生** | 烤好一批，过期了偷偷补烤 |

## 1. 对 SEO 站为什么重要

搜索引擎爬虫抓页面时，**CSR 可能抓到空壳**（内容靠 JS 才出来，爬虫不一定执行/等 JS）→ 不利 SEO。
**SSR/SSG/ISR 首屏 HTML 就带内容**，爬虫直接拿到 → 利于 SEO。所以 SEO 站基本用 SSR/SSG/ISR，不用纯 CSR。

## 2. 怎么选（Next App Router）

- **内容基本不变**（条款、关于页）→ **SSG**：构建时生成，最快，CDN 直接缓存。
- **内容会变但能容忍短暂旧**（列表、详情）→ **ISR**：静态 + 定时再生，兼顾快和新。
- **强依赖请求上下文/实时**（要读 host、cookie、每次都最新）→ **SSR（force-dynamic）**：每次请求实时渲染。
- **纯交互、不影响 SEO 的局部**（下拉、弹窗数据）→ 组件 **CSR**（客户端 fetch）。

## 3. 这次踩的坑（都和渲染模式有关）

### 坑 1：详情页 500 —— ISR 撞上"读 host"
详情页原本想用 ISR（`revalidate`），但页面里要**读请求头 host**（用于按域名路由后端）。**读 host 是"动态"操作，和 ISR 的"静态"本质冲突** → 生产 500。**解法：改 `force-dynamic`**（明确按请求实时渲染），不再尝试静态化。

### 坑 2：build 失败 —— 预渲染时调后端被 403
SSG/预渲染是在 **build 时**跑的。如果被预渲染的页面（或它的 layout）**在 build 时调后端**取数（如语言列表），而 build 环境调后端被网关 403/后端 503 → **整个构建失败**。
- 解法不是加假数据，而是：**配置类数据**（语言列表用前端本地常量）在失败时回退、**业务页**改动态渲染（运行时在 pod 内取），让 **build 不强依赖后端**。（详见我们那次 `webLanguage 403` 的修复。）

### 坑 3：SSR 取数走内网
C 端 SSR 是在 **pod 内（服务端）** 取数的，所以它走**集群内网 Service**（`xxx-seo-api:8080`）调后端，绕开公网网关——这也是"SSR"这个特性带来的（服务端发请求，不是浏览器发）。见《[Kubernetes与Pod](./Kubernetes与Pod-前端视角)》《[后端全景](./这套SEO项目的后端全景-前端视角)》。

## 4. 几个关键认知

- **"动态 API"会让页面变动态**：在页面里用 `headers()`/`cookies()`（读 host、读 cookie）会让 Next 判定这页必须动态渲染（不能 SSG/ISR）。想静态化就别在关键路径读这些。
- **SSG/ISR 的取数发生在 build 或再生时**，那时的环境（CI/构建机）不一定能连后端——所以 **build 不该强依赖后端可用**。
- **force-dynamic ≠ 慢/不利 SEO**：SSR 动态渲染的首屏 HTML 一样带内容、爬虫能抓，只是没有静态缓存、每次现做。对时效性强的页反而对。

## 5. 前端会撞见的

- **"生产详情页 500，本地好的"**：常见于 ISR/静态化 与 读 host/cookie 的冲突，或预渲染时后端不可用 → 考虑改 `force-dynamic` 或给取数容错。
- **"构建挂了，报某接口 403/超时"**：是 build 时预渲染调后端失败 → 让 build 不依赖后端（配置回退 + 业务页动态）。
- **列表/详情要不要静态化**：权衡"更新频率 vs 速度"，能 ISR 就 ISR，必须实时才 force-dynamic。

## 6. 一句话总结

- **CSR/SSR/SSG/ISR**：分别是"浏览器渲染 / 每次请求现做 / 构建时烤好 / 静态+定时再生"；SEO 站用 SSR/SSG/ISR，别用纯 CSR。
- **读 host/cookie 等动态 API 会强制动态渲染**，和 ISR/SSG 冲突（详情页 500 的根）。
- **build 时的预渲染不该强依赖后端**（否则后端一挂构建就失败）；SSR 取数在服务端、走内网。
