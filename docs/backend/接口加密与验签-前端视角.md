# 接口加密与验签 —— 前端视角：为什么后端返回一串看不懂的密文

> 背景：这次项目里，我用 curl 直接打后端接口，返回的不是 JSON，而是**一串 Base64 密文**（甚至"非法请求"）；埋点上报的 body 也是密文。作为前端，平时接口都是明文 JSON，第一次遇到"接口加密/验签"完全懵。这篇讲清楚：为什么要加密、怎么加解密、密钥放哪、以及前端联调时会撞见的坑。（密钥值本文一律脱敏，只讲机制。）

---

## 0. 先破个惊：接口返回密文是"正常的"

裸 curl 打这类接口，看到 Base64 乱码或"非法请求"——**不是接口坏了，是它本来就加密 + 要验签**。浏览器/SSR 里有对应的加解密逻辑，拿到密文会自动解密成 JSON；你手动 curl 没带那套逻辑，所以看到密文。

## 1. 为什么要加密接口

前端习惯明文 JSON，但 C 端接口（尤其内容/短剧这类）加密常见，目的：
- **防抓包扒接口**：别人抓包看不到明文参数/返回，增加逆向成本；
- **防刷/防伪造**：配合验签，请求被篡改就失效；
- **合规/资源保护**：播放地址、内容数据不想明文暴露。

不是"绝对安全"（前端能解密说明密钥在客户端侧或可获取），更多是**抬高门槛**。

## 2. 本项目的两套加密（场景不同、方案不同）

| | 业务接口 `app-api`（剧集/内容等） | 埋点上报 |
|---|---|---|
| 算法 | **AES-128-CBC**（PKCS7，Base64） | **AES-GCM**（随机 IV 前置，URL-safe Base64） |
| 加解密在哪 | **服务端**（Next SSR，`server-only`） | **浏览器端**（`window.crypto.subtle`） |
| 密钥放哪 | 服务端环境变量，**不下发浏览器** | 前端常量（`NEXT_PUBLIC_*`，**浏览器可见**） |
| 传输标记 | 请求头 `X-Encrypted: true` + `Language-Code` | 请求头 `App-Id`（区分产线） |

**为什么两套不一样？**
- 业务接口由 **SSR 服务端**发起，密钥能真正藏在服务端（`server-only`，打不进浏览器包）→ 用对称 CBC，密钥保密性好。
- 埋点由**浏览器直接上报**，密钥必须在前端 → 只能放 `NEXT_PUBLIC`，**浏览器里能看到**，所以埋点加密更多是"防明文/轻度混淆"，不是强保密；用 GCM（自带完整性校验）。

## 3. 加解密流程长什么样

**业务接口（服务端）**：
```
前端参数对象
  → AES-128-CBC 加密 → Base64 密文
  → POST，带 header: X-Encrypted: true, Language-Code: en
  → 后端解密、处理、返回【加密的响应】
  → 前端 AES 解密 → 拿到 JSON
```
关键：请求体是密文、响应也是密文，**加解密都在服务端做**，密钥不进浏览器。

**埋点（浏览器）**：
```
埋点 payload(JSON)
  → AES-GCM 加密(随机IV前置) → URL-safe Base64
  → POST 到事件服务，header: App-Id
  → 服务端解密入库
```

## 4. CBC 与 GCM 的区别（够用版）

- **CBC**：只加密，不带"防篡改校验"。需要额外验签才能防改。
- **GCM**：加密 + **自带完整性认证标签**（AEAD），密文被改会解密失败——所以埋点用 GCM，天然带防篡改。
- IV（初始向量）：CBC 这里用固定 IV（简化，安全性打折）；GCM 用**随机 IV 并前置**到密文里（更规范）。

## 5. 验签 / 防篡改（"非法请求"从哪来）

有些接口除了加密还**验签**：请求要带签名（如参数 + 密钥算的哈希），后端校验签名对不对、时间戳是否过期。不对就返回**"非法请求"**。这也是为什么你裸 curl（没算签名）会被拒。

## 6. 前端会撞见的坑

1. **裸 curl 返回密文/非法请求 = 正常**，不代表接口挂了；想看明文得走带解密逻辑的客户端，或用联调工具带上密钥。
2. **联调时密钥必须两端一致**：前端解密 key 和后端加密 key 对不上 → 解出乱码/"解密结果为空"。换环境要确认密钥一致。
3. **密钥别泄露**：
   - 业务密钥要 `server-only` + 环境变量，**严禁打进浏览器包**（别用 `NEXT_PUBLIC_` 前缀暴露）；
   - 埋点密钥因为必须在前端，本就是半公开的，别拿它保护重要数据。
4. **响应信封两种形态**：有的直接返回密文字符串，有的包成 `{ data: "密文" }`——解密逻辑要都兼容。

## 7. 一句话总结

- 接口返回密文是**故意加密**（防抓包/防刷/混淆），不是坏了。
- 本项目两套：**业务 app-api = AES-CBC，密钥服务端保密（SSR 加解密）**；**埋点 = AES-GCM，密钥在浏览器（半公开、防明文）**。
- 前端要点：**裸 curl 看到密文别慌、联调密钥两端要一致、业务密钥绝不进浏览器**。
