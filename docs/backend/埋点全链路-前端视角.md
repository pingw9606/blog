# 埋点从前端到数仓全链路 —— 前端视角：一次点击是怎么变成一行数据的

> 背景：这次项目最花精力的就是埋点——对齐老站事件、排查参数、换上报域名（CNAME/证书/CORS 连环坑）、最后到 StarRocks 查库验证。作为前端，我以前只知道"调个 track 上报"，但一次点击从浏览器出发、到能在数仓里被查到，中间这条链路是完全的黑盒。这篇把它整条串起来。

---

## 0. 全链路一张图

```
浏览器 track('reel_click', {...})
  │  ① 组装 payload + ② AES-GCM 加密 + ③ header 带 App-Id(产线)
  ▼
埋点事件服务 (shorttv-app-event)
  │  ④ 解密、校验、读 App-Id
  ▼
Kafka (异步传送带，削峰解耦)
  │  ⑤ 数仓消费
  ▼
StarRocks · ods.web_event (列存，供分析)
  │  ⑥ 你用 SQL 按 server_app_id 查
  ▼
看板 / 分析 / 排查
```

## 1. 前端这一端：track 干了什么

调用很简单：`track('reel_click', { reel_id, from, scene })`。内部做了三件事：
1. **组装 payload**：`{ eventCode, clientCreateAt, ua, clientIp, languageCode, remark: { deviceType, fingerprint, visitorId, ...你传的参数 } }`。注意——**你传的自定义参数（scene/reel_id 等）塞进 `remark`**，另有 `from/pageName` 等可能是顶层字段。
2. **加密**：payload 用 **AES-GCM** 加密（见《[接口加密与验签](./接口加密与验签-前端视角)》）。
3. **上报**：`fetch` POST 到事件服务，`keepalive: true`（页面卸载也能发完），header 带 **`App-Id`（区分产线）**。

> 关键：**产线不在 payload 里，在 HTTP header `App-Id`**（VibeShort=2616）。这决定了后面查库用哪个字段。

## 2. 事件服务 + Kafka：为什么不直接写库

浏览器把事件 POST 给事件服务，服务**没有直接写数据库**，而是丢进 **Kafka**：
- 埋点量巨大（每次点击/曝光一条），直写库扛不住；
- 不能因为写库慢/挂了就阻塞用户；
- 下游不止一个（入库 + 实时大盘 + 算法）。

Kafka 当"缓冲传送带"，异步、削峰、解耦（详见《[消息队列与Kafka](./消息队列与Kafka-前端视角)》）。数仓侧消费者再把数据落到 StarRocks。

## 3. 数仓这一端：落到 StarRocks，查询有讲究

数据最终进 **StarRocks 的 `ods.web_event`**（列存分析库，见《[看懂DMS里的数据库实例](./看懂DMS里的数据库实例-前端视角)》）。查的时候有两个**大坑**（这次踩的）：

### 坑 1：产线字段是 `server_app_id`，不是 `app_id`
- 前端只在 **header** 传 `App-Id`，payload 里**没有 app_id**；
- 服务端读 header 后落库到列 **`server_app_id`**（VibeShort=2616）；
- 表里还有个 `app_id` 列，那是**别的来源（App/广告端）自带的**，web 埋点这列是空的。
- **所以查站点埋点必须 `WHERE server_app_id = '2616'`，用 `app_id` 查不到。**

### 坑 2：别裸 SELECT *、必须加时间范围
`web_event` 是亿级大表，裸查会卡死。标准姿势：
```sql
SELECT event_code, server_app_id, server_time, remark
FROM ods.web_event
WHERE server_app_id = '2616'                  -- 产线
  AND server_time >= '2026-07-21 00:00:00'     -- 时间范围走分区
ORDER BY server_time DESC LIMIT 20;
```
自定义参数（scene/reel_id）在 `remark` JSON 里，用 `get_json_string(remark,'$.scene')` 解析；`from/page_name` 等可能是独立列。

## 4. 怎么验证"埋点通了"

三步：
1. **网络层**：浏览器 Network 里 `event 上报请求` 是不是 200（不是 CORS 403、不是 DNS 失败）；
2. **有没有数据**：StarRocks 按 `server_app_id='2616' + 今天` 查有没有新记录；
3. **事件/参数对不对**：按 `event_code` 统计各事件量、抽查 `remark` 里参数（scene/from/reel_id）是否符合规格。

## 5. 这次踩的坑合集（都在别的篇详解）

- **上报域名换成品牌域名**（`event.vibeshort.live` CNAME 到共用事件服务，隐藏关联）→ 连环踩 **DNS 拼写 / 证书不匹配 / CORS 白名单 / 灰度没全量**（见《[换域名为什么还不通](./换域名为什么还不通-CNAME证书CORS-前端视角)》《[灰度发布](./灰度发布-前端视角)》）。
- **参数对齐**：老站每个页面各自埋、参数给全；新站组件复用后容易漏埋/写死 scene/缺参数——要按场景把 `from/scene/seconds` 等传对。
- **App-Id 区分产线**：多产品共用一套埋点服务，靠 App-Id；查库对应 `server_app_id`。

## 6. 一句话总结

- 一次点击：**前端 track（组 payload + GCM 加密 + header 带 App-Id）→ 事件服务 → Kafka → StarRocks `ods.web_event`**。
- 前端记两件事：**产线走 header `App-Id`（查库是 `server_app_id`，不是 app_id）**；**验证埋点 = 看上报 200 + 查库有数据 + 抽查参数**。
- 换上报域名不是配个 CNAME 就完事，还有证书/CORS/全量部署几关。
