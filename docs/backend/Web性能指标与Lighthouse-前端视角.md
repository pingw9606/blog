# Web 性能指标与 Lighthouse —— 前端视角：用真实竞品对比学会读性能数据

> 背景：这次拿我们的站和竞品做了轮性能对比（curl 网络层 + Lighthouse）。借这份真实数据，把 Web 性能的核心指标（FCP/LCP/TBT/CLS…）、怎么测、以及优化优先级讲清楚——顺便纠正一个常见误区：**"资源越小越快"并不成立**。

---

## 0. 先认识核心指标（Core Web Vitals + 常用项）

| 指标 | 全称 | 衡量什么 | Google "良好"线 |
|---|---|---|---|
| **FCP** | First Contentful Paint | 首次画出内容（用户看到"有东西"） | < 1.8s |
| **LCP** | Largest Contentful Paint | 最大内容（通常首屏大图/大标题）画完 | **< 2.5s** |
| **TBT** | Total Blocking Time | 主线程被 JS 阻塞的总时长（卡不卡） | < 200ms |
| **CLS** | Cumulative Layout Shift | 布局偏移量（页面跳不跳） | **< 0.1** |
| **SI** | Speed Index | 首屏内容填充的快慢 | 越低越好 |
| **TTI** | Time to Interactive | 多久能稳定交互 | 越低越好 |

其中 **LCP / CLS / (INP)** 是 Google 的 **Core Web Vitals**，直接影响 SEO 排名——对 SEO 站尤其重要。

## 1. 怎么测（两个工具，测的东西不同）

- **curl**：测**网络层**——DNS、TCP、TLS、TTFB(首字节)、下载时间、体积。快，但**只到 HTML 文档**，不含渲染。
  ```bash
  curl -s -o /dev/null -w "dns=%{time_namelookup} tcp=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total}\n" https://xxx/
  ```
- **Lighthouse**：起无头 Chrome 真实加载页面，测**渲染层**——FCP/LCP/TBT/CLS/性能分。这才是"用户体验"级别的指标。
  ```bash
  npx lighthouse https://xxx/ --only-categories=performance --preset=desktop --output=json --output-path=out.json
  ```

## 2. 一份真实对比（我们 vs 竞品，桌面版）

| 指标 | 我们（预发） | 竞品（生产） | 谁好 |
|---|---|---|---|
| 性能总分 | 61 | 83 | 竞品 |
| FCP | 2.7s | 1.0s | 竞品 |
| **LCP** | **4.6s** ⚠️ | 2.1s | 竞品（我们超了 2.5s 线） |
| TTI | 4.6s | 3.0s | 竞品 |
| **TBT** | **0ms** ✅ | 30ms | **我们** |
| **CLS** | **0.006** ✅ | 0.038 | **我们** |

**读法**：我们**慢在"首屏出现速度"（FCP/LCP）**，但**强在"交互流畅 + 布局稳定"（TBT/CLS）**。说明我们 JS 不阻塞主线程、页面不抖（框架用得好），但内容/图片多久能看到偏慢。

## 3. 误区纠正：资源越小越快？不一定

对比资源体积时发现反直觉的一幕：
- 我们首页总负载 **2.9MB**，竞品 **7.0MB**（竟然比我们大一倍多）；
- 但竞品 LCP 2.1s，比我们 4.6s 快一倍。

**为什么资源更大反而更快？** 因为竞品有 **CDN 边缘加速 + 图片懒加载**（首屏只加载可见的，其余滚动再加载）。所以——
> **快慢不看"资源总量"，看"首屏关键路径快不快"。** 总量大但首屏关键资源加载快，照样快。

## 4. 怎么定位瓶颈（别拍脑袋）

看 Lighthouse 的诊断/机会项 + 资源构成。我们这次定位到：
1. **没 CDN + 源站远**（curl：建连 0.5s vs 竞品 0.16s）→ 拖 FCP/LCP。
2. **字体 733KB / 8 个文件**（竞品才 209KB/3个）→ 阻塞文字渲染，拖 FCP。
3. 图片：Lighthouse **没报**图片问题（格式/尺寸/懒加载都通过）→ 说明 `next/image` 已优化到位，**再抠图片收益很小**。

## 5. 优化优先级（按投入产出比）

| 优先级 | 措施 | 为什么 |
|---|---|---|
| 🔥 高 | **接 CDN** | 抹平建连+传输慢，FCP/LCP 一起降，收益最大 |
| 🔥 较高 | **字体瘦身**（按需/子集化/`font-display:swap`/preload） | 733KB 直接卡 FCP |
| 💧 低 | 图片优化 | 已经优化过了，Lighthouse 没挑出问题，受"没 CDN"封顶 |
| 保持 | TBT/CLS | 已优秀，别搞坏 |

## 6. 两个重要提醒

1. **预发 ≠ 生产**：我们测的是预发（大概率没接 CDN），这 61 分不代表生产水平；要对标应拿**生产**再测。
2. **别只看总分**：61 vs 83 不代表"全面落后"——拆开看，我们交互/稳定性更好，只是首屏慢。优化要**打在具体指标（LCP）** 上，而不是笼统"提性能分"。

## 7. 一句话总结

- 记住 **LCP(<2.5s)、CLS(<0.1)** 是影响 SEO 的核心指标；FCP/TBT 辅助。
- **curl 测网络层、Lighthouse 测渲染层**，配合定位。
- **快慢看首屏关键路径，不看资源总量**；优化优先级 **CDN > 字体 > 图片（已优化就别抠）**。
- 结论要落到**具体指标**，并注意**预发/生产差异**。
