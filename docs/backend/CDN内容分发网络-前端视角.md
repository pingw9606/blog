# CDN 内容分发网络 —— 前端视角：为什么竞品建连比我们快 3 倍

> 背景：这次做性能对比，发现竞品站每次 TCP+TLS 建连只要 ~0.16s，我们预发要 ~0.5s（慢 3 倍）。差别就在——竞品用了 **CDN（Cloudflare）**，节点就在新加坡（离用户近）；我们直连远端源站。这篇把 CDN 讲清楚。

---

## 0. 一句话：CDN = 把内容"就近"放到离用户最近的节点

CDN（Content Delivery Network，内容分发网络）在全球/全国部署很多**边缘节点**，把你的静态资源（JS/CSS/图片/视频）缓存一份到各节点。用户访问时，从**离他最近的节点**取，而不是大老远回你的源站。

**前端类比**：源站是"总仓库"（可能在美国），CDN 是遍布各地的"就近便利店"。用户不用跑到总仓库，就近的便利店就有货 → 快。

## 1. 为什么快（对上这次的数据）

- **建连快**：节点离用户近，TCP/TLS 握手的物理往返短。竞品新加坡节点 vs 我们远端源站，就是那 0.16s vs 0.5s 的差距。
- **命中缓存不回源**：静态资源在边缘节点直接返回，不用每次都回源站，又快又减源站压力。
- **HTTP/2、Brotli、TLS 优化** 等边缘节点通常都配好了。

## 2. 动静分离：CDN 只加速"静态"

CDN 主要缓存**静态资源**（JS/CSS/图片/字体/视频切片）。**动态内容**（个性化接口、SSR 页面）通常"回源"或按规则缓存（竞品响应里 `cf-cache-status: DYNAMIC` 就是动态回源）。

所以典型架构：**静态走 CDN 边缘，动态请求穿透 CDN 回到源站/网关。**

## 3. 前端最该知道的坑：CDN 缓存 vs 发版更新

CDN 会缓存资源，**发版后可能还返回旧的**。所以：
- **带 hash 的静态资源**（`app.a1b2c3.js`）：内容变文件名就变，可**长期强缓存**（`immutable`），安全。
- **HTML 文档**：不能长缓存，否则发版后用户还看到旧页面 → 通常设 `no-cache` 每次校验。
- 发版后有时要**刷新/预热 CDN 缓存**（purge），否则旧缓存还在。

（我们项目 `next.config` 里就特意区分了：`/_next/static` 长缓存 immutable、HTML no-cache——就是为这个。）

## 4. CDN 还能做的

- **防盗链**：按 `Referer`/来源域名白名单，只允许自己站点引用图片/视频，别人盗链直接拒（比用 `Sec-Fetch` 头更靠谱）。
- **抗攻击**：吸收 DDoS、隐藏源站 IP。
- **图片处理**：不少 CDN 支持按 URL 参数实时裁剪/转 WebP。

## 5. 结合本项目

- **竞品有 Cloudflare，我们预发没接 CDN** → 建连慢、首屏(FCP/LCP)被拖（见《[Web性能指标与Lighthouse](./Web性能指标与Lighthouse-前端视角)》）。
- **优化建议里 CDN 是收益最高项**：接 CDN 能一举抹平建连+传输差距，静态资源/图片/字体全都边缘加速。
- 埋点/接口这类**动态请求**不靠 CDN 加速（甚至要穿透回源），别指望 CDN 解决接口慢。

## 6. 一句话总结

- **CDN = 就近节点缓存静态资源**，靠"离用户近 + 命中缓存不回源"提速；这次竞品建连快 3 倍就是 CDN 的功劳。
- **动静分离**：静态走 CDN，动态回源。
- 前端必知：**hash 资源长缓存、HTML 不缓存、发版可能要刷 CDN**；防盗链用 Referer 白名单。
