# Kubernetes 与 Pod —— 前端视角：服务跑在哪、谁在管、为什么总是"多个"

> 背景：这次项目里 `pod`、`Service`、`EKS`、`多节点`、`滚动/灰度` 这些词满天飞——"C 端 SSR 跑在 pod 里"、"走内网 Service `aidrama-seo-api:8080`"、"两个节点没全更新"……作为前端只知道"部署上线"，K8s 是纯黑盒。这篇把容器 / Pod / K8s 从前端视角讲清楚，正好把之前散在《灰度发布》《XXL-Job》《后端全景》里的 pod 概念串起来。

---

## 0. 三层概念：容器 → Pod → Kubernetes

| 概念 | 是什么 | 前端类比 |
|---|---|---|
| **容器（Docker）** | 把应用 + 运行环境打包成一个标准盒子，哪都能跑 | 一个"装好依赖、开箱即用"的应用镜像 |
| **Pod** | K8s 里**最小的部署单元** = 一个"活着"的应用实例（通常裹 1 个容器） | 一个正在运行的服务进程实例 |
| **Kubernetes（K8s）** | 管理一大堆 Pod 的**调度中心/物业** | 自动帮你开关机、扩容、重启、滚动更新的"运维大脑" |

一句话：**代码 → 打成容器镜像 → K8s 把镜像跑成一个个 Pod → 一堆 Pod 对外提供服务。**

## 1. Pod 是什么：一个"应用实例"

你的后端/前端服务部署上去，就是变成 **N 个 Pod 在跑**（N 个副本）。每个 Pod 是一个独立运行的实例，有自己的临时 IP。**Pod 是会变的**——挂了 K8s 自动拉新的、扩容加几个、更新时换新的，IP 都会变。

> 关键：**Pod 是"一次性、可替换"的**。别指望某个 Pod 一直在、IP 不变。这也是为什么需要下面的 Service。

## 2. Service：一组 Pod 的"稳定入口"

Pod 会变、IP 会换，那别的服务怎么稳定地找到它？靠 **Service**——给一组 Pod 一个**固定的内网名字**，请求发给这个名字，K8s 自动转发到背后某个健康的 Pod。

这次项目里你见过的 `http://aidrama-seo-api:8080` **就是一个 K8s Service**：
- `aidrama-seo-api` 是 Service 名（内网稳定，不管后面 Pod 怎么变）；
- 谁在集群内访问它，就被转发到后端的某个 Pod。

**C 端 SSR 为什么走它**：Next 在 **pod 内（服务端）** 调后端，走**内网 Service** `aidrama-seo-api:8080` 直连，绕开公网网关（公网被网关白名单 403）。这就是《后端全景》里说的"SSR 走内网"。

## 3. K8s 到底帮你干了什么

- **多副本 + 负载均衡**：同一个服务跑多个 Pod，流量分摊，一个挂了还有别的。
- **自愈**：Pod 崩了/健康检查失败，自动重启或换新的。
- **弹性伸缩**：流量大自动加 Pod，流量小减 Pod。
- **滚动更新 / 灰度**：发新版本时**逐个 Pod 替换**（不是一刀切），可以先换一部分（灰度），没问题再全量。
- **配置/密钥注入**：把配置（如连 Nacos 的地址）通过环境变量注入 Pod。

## 4. 前端会撞见 Pod 的几个真实场景（这次全踩过）

1. **内网 Service 调用**：C 端 SSR 走 `xxx-seo-api:8080` 调后端——这是 Pod 间通过 Service 内网通信，不出公网。
2. **"多个 Pod" 带来的坑**：
   - **定时任务重复执行**：代码里写死 `@Scheduled`，3 个 Pod 到点各跑一遍 → 用 XXL-Job 统一调度只跑一次（见《[定时任务与XXL-Job](./定时任务与XXL-Job-前端视角)》）。
   - **灰度没全量**：滚动更新只换了部分 Pod/节点，请求打到新旧 Pod 结果不一致、时通时不通（见《[灰度发布](./灰度发布-前端视角)》——那次埋点 CORS 就是两个节点没全更新）。
3. **看日志要看对 Pod**：一个服务多个 Pod，各有各的日志。查问题（比如 `[api]` 日志）要确认看的是处理你请求的那个 Pod，或看聚合日志。
4. **EKS**：就是 **AWS 托管的 Kubernetes**（Elastic Kubernetes Service）。这次 `shorttv-app-event-eks` 就是跑在 EKS 上的服务；而域名当时还指着老的裸 EC2（不是 EKS），才导致"部署了没生效"。

## 5. 一张图

```
        你的代码 ──打包──▶ 容器镜像 ──K8s 调度──▶ 一堆 Pod
                                                  │(Pod会变/会扩缩/会重启)
                          ┌───────── Service（固定内网名，如 aidrama-seo-api:8080）
                          │           把请求转发到某个健康 Pod
   集群内其它服务/SSR ─────┘
                          ┌── Pod A (v1)  ┐
                          ├── Pod B (v1)  ├─ 多副本：负载均衡 + 自愈 + 滚动更新
                          └── Pod C (v2)  ┘ ← 灰度：只有它先换了新版本
   公网用户 ──▶ 网关(白名单) ──▶ Service/Ingress ──▶ Pod
```

## 6. 一句话总结

- **Pod = 一个应用实例**（可替换、IP 会变、通常有多个副本）；**Service = 一组 Pod 的稳定内网入口**（`xxx:8080` 那种）；**K8s = 管这堆 Pod 的调度大脑**（自愈/伸缩/滚动更新）。
- 前端要知道：**你的服务上线后是"多个 Pod 在跑"**——这解释了很多现象：SSR 走内网 Service、定时任务为什么会重复、灰度为什么时通时不通、看日志为什么要认准 Pod。
- 遇到"部署了没生效"，先想：**部署的对象和流量实际打到的 Pod/节点，是不是同一批？**（这次 EKS vs 老 EC2 就是这个坑。）
