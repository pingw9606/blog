# 定时任务与 XXL-Job —— 前端视角：后端"到点自动跑"是怎么调度的

> 背景：一次排查里运维提到"后端还有三个 job"，我一脸问号——这些"job（定时任务）"是什么、几点跑、谁触发的？后端还引了个叫 `xxl-job` 的东西。作为前端，我们对"定时执行"的理解基本停在 `setInterval`，这篇就把后端的定时任务体系讲清楚。整套系统见《[这套SEO项目的后端全景](./这套SEO项目的后端全景-前端视角)》。

---

## 0. 什么是"定时任务 / cron job"

就是**到了某个时间点、自动执行的一段逻辑**。后端常见需求：
- 每天凌晨 2 点汇总昨天的数据；
- 每 5 分钟刷一次缓存；
- 每小时清理一次过期数据。

这些不是用户触发的，是**系统按时间自己跑**的——这就是定时任务（job），"cron" 是 Linux 上定时任务的老祖宗，"cron job" 泛指这类活。

## 1. 前端类比：`setInterval` 的"企业版"

前端要定时干活会用：
```js
setInterval(() => doSomething(), 60 * 1000) // 每分钟
```
后端也有类似的（Spring 的 `@Scheduled`），但一到**生产环境**就有一堆 `setInterval` 解决不了的问题——于是有了 **XXL-Job** 这种专业调度平台。

## 2. cron 表达式：怎么描述"几点跑"

定时任务用 **cron 表达式** 描述执行时间，长这样：
```
0 0 2 * * ?      → 每天凌晨 2:00:00
0 */5 * * * ?    → 每 5 分钟
0 0 * * * ?      → 每小时整点
```
（从左到右大致是：秒 分 时 日 月 周。前端看个眼熟就行，改的时候网上有可视化生成器。）

## 3. 为什么不用代码里的 `@Scheduled`（关键）

最土的做法是把定时器写死在代码里（`@Scheduled(cron="...")`）。单机没问题，但**生产环境有致命坑**：

### 坑：多实例重复执行
我们后端在 K8s 部署**多个 pod**（多个副本）。如果定时器写在代码里，**每个 pod 到点都会各跑一遍**：
```
凌晨2点，3个pod → 同一个"数据汇总"跑了 3 次 → 数据被算了3遍，出乱子
```

还有：改执行时间要重新发版、跑失败没人知道、没法临时停某个任务……

**XXL-Job 就是来解决这些的。**

## 4. XXL-Job 是什么：调度中心 + 执行器

XXL-Job 是个**分布式定时任务调度平台**，两部分：

```
┌─────────────────┐   到点了，RPC 触发   ┌──────────────────────┐
│ 调度中心          │ ───────────────────▶ │ 执行器(跑在后端应用里)   │
│ xxl-job-admin    │                      │ 引入 xxl-job-core      │
│ (Web后台:配cron/ │ ◀─────────────────── │ 用 @XxlJob("xxx") 写   │
│  启停/看执行日志) │    上报执行结果       │ 具体任务逻辑            │
└─────────────────┘                      └──────────────────────┘
```

- **调度中心（xxl-job-admin）**：一个 Web 后台，负责"**何时跑**"——cron 表达式、启停、参数、失败报警、执行日志，都在这里配、这里看。
- **执行器**：就是我们的后端应用（引入 `xxl-job-core`），里面用 `@XxlJob("handlerName")` 写"**跑什么**"。启动后注册到调度中心。
- **分工**：**"何时"在后台配，"做什么"在代码里写**，解耦。

## 5. 它解决了什么（对比代码里的定时器）

1. **多实例不重复跑**（最关键）：调度中心**统一派发，只让一个实例执行一次**——多 pod 也不会重复算。
2. **可视化 + 在线改**：所有任务在一个后台管，改 cron / 停某个任务 / 手动触发一次，**点几下就行，不用改代码发版**。
3. **可靠**：失败自动重试、超时控制、失败报警、每次执行日志留档可查。

## 6. 我们项目怎么用

- 后端 `storyreel-seo-api` 引了 `xxl-job-core`，作为**执行器**注册到 XXL-Job 调度中心（admin 地址+token 配在 Nacos 里）。
- 所谓的**"三个 job"** = 调度中心里配的三个定时任务，到点触发后端跑对应逻辑。
- **上线要点**：① 后端能连上调度中心；② 在调度中心把这几个 job 配好（执行器、cron、启停）——否则定时逻辑不会跑。

## 7. 前端会在什么时候撞见它

- **某个"应该定时更新的数据"没更新 / 或被重复处理**——可能是对应的 XXL-Job 没跑 / 配置停了 / 或退回了代码定时器导致多 pod 重复。
- 想知道"这个定时逻辑几点跑、跑没跑成功"——去 **XXL-Job 调度中心的 Web 后台**「任务管理 / 调度日志」里看，一目了然（问后端/运维要地址）。

## 8. 一句话总结

- **定时任务 = 到点自动执行的逻辑**，用 cron 表达式描述时间。
- **别在多实例的代码里裸写 `@Scheduled`**——会重复执行；用 **XXL-Job**：调度中心管"何时跑"、执行器（后端应用）管"跑什么"，统一派发只跑一次，还能可视化配置 / 失败重试 / 看日志。
- 前端遇到"定时数据没更新 / 重复处理"，先去 XXL-Job 调度中心看那个 job 的状态和日志。
