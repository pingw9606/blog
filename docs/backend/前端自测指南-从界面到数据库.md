# 前端自测指南 —— 从「界面点点点」到「落库验证」

> 背景：团队没有专职测试，前端要自己兜测试这一环。很多前端做测试就是「界面点一点，能跑就行」，但真正的测试远不止于此——**一次操作在界面上成功了，不代表数据真的对了**。这篇把「前端如何系统地自测」拆开讲：要验证哪几层、用什么工具、常见场景怎么操作、以及一份可直接抄的自测 checklist。
>
> 例子结合我们实际的技术栈：Next.js SEO 站（SSR/SSG）+ yudao 后台（Vue3）+ 自研埋点 + 阿里云 RDS（MySQL）。

---

## 0. 先建立一个观念：一次操作要验证「四层」

新手测试只看**第一层**，出问题的往往在后面三层：

| 层 | 验证什么 | 典型翻车 |
|---|---|---|
| ① 界面层 | 点了有没有反应、提示对不对、跳转对不对 | 按钮点了没反应、报错弹窗一闪而过 |
| ② 接口层 | 请求发了没、参数对不对、响应对不对 | 前端提示「成功」，其实接口 500 被吞了 |
| ③ 数据层 | **有没有真的落库、字段存对没** | 界面显示成功，数据库根本没写进去 / 写错字段 |
| ④ 一致性层 | 刷新后还在吗、其它页面/端能看到吗、缓存对吗 | 当前页对了，刷新就没了；后台改了前台不更新 |

> 记住这句话：**「界面成功」只是表象，要顺着「界面 → 接口 → 数据库」一路验证到底。**

---

## 1. 必备工具（先把家伙备齐）

| 工具 | 干什么 | 场景 |
|---|---|---|
| **浏览器 DevTools** | 看请求/控制台/存储 | 每次测试都开着（F12） |
| **数据库客户端**（TablePlus / DBeaver） | 查落库、核对字段 | 验证第 ③ 层 |
| **接口工具**（Postman / Apifox / YApi） | 单独调接口、造异常入参 | 绕过界面直接测接口 |
| **抓包工具**（Charles / Proxyman） | 抓移动端/真机请求 | 测手机 H5、真机埋点 |

DevTools 三个面板最常用：
- **Network**：看每个请求的 URL、请求头、请求体、响应、状态码、耗时。
- **Console**：看报错、打日志。注意有没有被 `try/catch` 吞掉的错误。
- **Application**：看 Cookie / localStorage / SessionStorage（登录态、语言、埋点 visitorId 都在这）。

## 2. 逐层怎么测

### ① 界面层：点点点也要有章法

不是乱点，按这几类覆盖：
- **正常流程**：主路径走通（如：登录 → 进列表 → 新建 → 提交 → 列表出现新数据）。
- **反馈是否正确**：成功/失败提示、loading 态、按钮禁用（防重复提交）、空态（没数据时的占位）。
- **边界输入**：空值、超长文本、特殊字符（`<script>`、emoji、中文）、0/负数、超大数字。
- **异常操作**：断网点提交、快速连点、重复提交、返回上一步再提交。

### ② 接口层：打开 Network，别只看界面

操作后立刻看 Network 里对应请求：

- **状态码**：200 不代表成功！很多后端 200 里包着 `{code: 500, msg: "xxx"}`。要**展开响应体看业务 code**。
- **请求参数**：Payload 里字段对不对、值对不对（尤其分页、筛选、id）。
- **请求头**：登录 token 带了没、我们埋点的 `App-Id` 对不对（VibeShort=2616 / StoryReel=2617）。
- **响应体**：返回的数据结构、字段是否为 null（前端崩溃常因为某字段后端返回 null）。

> 实战教训：我们首页曾因为某条剧集 `title` 后端返回 `null`，前端 `slug` 生成时 `null.toLowerCase()` 直接把整个页面 SSR 搞崩。**测试时就该在 Network 里留意「有没有字段是 null」**，而不是等它炸。

### ③ 数据层：落库没落库，查库说了算 ⭐

这是前端最容易漏、但最能体现测试水平的一层。**界面显示「保存成功」，一定要去数据库确认真的写进去了、且字段对**。

**用什么工具查库？** 我们后端是 MySQL（阿里云 RDS），常用可视化客户端：

| 工具 | 特点 | 建议 |
|---|---|---|
| **TablePlus** | Mac 原生、轻快、界面清爽 | 首选，免费版够用（限同时 2 个标签） |
| **DBeaver** | 开源全免费、功能全、跨库 | 功能最全，但基于 Java 略重、偶尔卡 |
| **Sequel Ace** | 专做 MySQL、极轻量、开源 | 只连 MySQL 时最省事 |
| **Navicat** | 老牌功能强 | 收费，团队有 license 才用 |
| DataGrip | JetBrains 系、SQL 补全强 | 用 IDEA 全家桶的人顺手 |

装好后新建 MySQL 连接，填 **Host / Port(3306) / User / Password / Database** 即可（连接信息问后端或看配置，注意区分测试库/生产库）。不想装客户端、只是偶尔查，也可以让后端帮跑 SQL，或用后端提供的数据库管理页。

以「后台新建一个 Banner」为例：

1. 后台点保存，界面提示成功。
2. 打开 TablePlus 连测试库，找到对应表（如 `web_banner`）。
3. 执行 SQL 确认：
   ```sql
   -- 按创建时间倒序，看最新一条是不是刚建的
   SELECT id, short_play_id, title, status, sort, create_time
   FROM web_banner
   ORDER BY create_time DESC
   LIMIT 5;
   ```
4. 核对：字段值和你填的一致吗？`status`（启用/停用）对吗？关联的 `short_play_id` 对吗？软删除字段 `deleted` 是 0 吗？

要重点查的几类字段：
- **关联字段**：外键 id 有没有存对（如 banner 关联的剧集 id）。
- **状态/枚举字段**：`status`、`type` 存的值对不对（前端选「启用」，库里是不是对应的 1）。
- **软删除**：很多系统是逻辑删除，删除操作要看 `deleted` 字段变了没，而不是记录消失。
- **时间/操作人**：`create_time`、`creator`、`update_time` 有没有正确写入。
- **多产品线隔离**：我们是一套代码多产线，注意数据有没有带对 `app_id` / 产线标识，别把 A 产线数据写进 B。

> 小技巧：不确定操作对应哪张表？在后台做一次操作，去 Network 看接口路径（如 `/webBanner/create`），再结合后端同学或表名规律（`web_banner`）定位。

### ④ 一致性层：刷新 / 换端 / 缓存

- **刷新还在吗**：新建/编辑后刷新页面，数据还在（确认真落库，不是前端内存假象）。
- **多端一致**：后台改了，前台展示跟着变吗？（注意有没有缓存/CDN/定时任务延迟）
- **缓存陷阱**：我们前台是 Next.js，有 SSG/ISR/fetch 缓存。后台改了数据前台没变，可能是**页面被静态缓存**了，不一定是 bug——要分清「缓存未过期」和「真没更新」。
- **多语言**：改了一个语种，其它语种对不对、有没有 fallback。

## 3. 前端特有的几个坑（我们项目相关）

- **SSR/SSG vs CSR**：SSR 页面的数据在**服务端**取，报错会体现在服务端日志或 build 阶段（如 prerender 崩溃），不是浏览器 Console。测 SSR 页要注意「首屏 HTML 里有没有内容」（右键查看网页源代码，不是 F12 的 Elements）。
- **埋点验证**：埋点是「静默上报」，界面看不出来。验证方法——Network 里筛 `event` 请求，确认：请求发出了、`App-Id` header 对（产线对）、payload 加密了、状态 200。漏埋点在界面上完全无感，必须靠 Network 抓。
- **SEO 相关**：title/description/canonical/hreflang 这些在 `<head>` 里，用「查看网页源代码」或 SEO 插件看，别只看页面渲染。
- **移动端 / 真机**：手机 H5 的问题（点击、软键盘、安全区、唤端）PC 模拟器测不全，重要功能要真机 + 抓包（Charles）。

## 4. 造数据与清理

- **造数据**：测试常需要特定数据（如「没有标题的剧」「超长标题」「过期的活动」）。优先通过后台/接口造；实在不行让后端或自己在测试库 `INSERT`（记得只在**测试库**，别碰生产）。
- **测完清理**：自己造的脏数据测完删掉，避免污染测试环境、影响别人。删之前确认是逻辑删除还是物理删除。
- **红线**：改测试库前先确认连的是测试库（看 host，别连成生产 RDS）；写操作前想清楚影响范围。

## 5. 一份可直接抄的「自测 Checklist」

提测/自测前，对着过一遍：

```
【功能】
☐ 主流程走通（增删改查各来一遍）
☐ 成功/失败提示正确，loading 和防重复提交有
☐ 空态、无数据、无权限的表现正常

【接口】(Network)
☐ 请求参数正确（分页/筛选/id）
☐ 业务 code 成功（不只是 HTTP 200）
☐ 响应字段无异常 null，结构符合预期
☐ 登录态 / App-Id 等关键 header 正确

【数据】(查库)
☐ 新增：库里有记录，字段值正确
☐ 编辑：对应记录字段更新了
☐ 删除：逻辑删除 deleted 置位（或物理删除消失）
☐ 关联/枚举/时间/操作人/产线标识 存对
☐ 刷新页面数据仍在

【边界异常】
☐ 空值 / 超长 / 特殊字符 / 重复提交
☐ 断网、快速连点

【兼容 & 一致性】
☐ Chrome / Safari / 移动端表现一致
☐ 后台改动前台正确反映（注意缓存）
☐ 多语言正确

【前端特有】
☐ SSR 首屏源代码有内容
☐ 埋点上报（Network 有 event 且 App-Id 对）
☐ SEO 头部（title/canonical/hreflang）正确
```

## 6. 常见误区

1. **只看界面「成功」提示** → 提示是前端写死的，接口失败也可能弹「成功」。要看 Network + 查库。
2. **HTTP 200 就以为成功** → 业务 code 才算数。
3. **不查库** → 落库没落库是数据正确性的最后一道关，前端最该补的就是这一环。
4. **只测「正常路径」** → 线上 bug 大多在边界和异常场景。
5. **测完不清理脏数据** → 污染环境，下次测试或别人踩坑。
6. **把缓存当 bug（或把 bug 当缓存）** → 分清是缓存未过期还是数据真没更新。

---

## 结语

前端做测试，核心是**从「点点点」升级到「顺着数据链路验证」**：界面 → Network 看接口 → 数据库查落库 → 刷新/换端看一致性。工具上把 DevTools 和一个数据库客户端用熟，思维上永远多问一句「界面成功了，数据真的对吗？」，就已经超过大多数「只点点点」的自测了。
