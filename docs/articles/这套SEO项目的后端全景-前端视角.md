# 这套 SEO 项目的后端全景 —— 前端视角：Nacos、内外网与一次请求的旅程

> 背景：我在做一个 SEO 独立站项目（Next.js C 端 + Vue3 后台 + Java/yudao 后端，一份后端代码跑 vibeshort / storyreel 多个产品）。作为前端，我发现"页面之外"全是盲区：**Nacos 是啥、为什么 C 端和后台调同一个后端却走两条路、埋点数据去哪了、登录报个"OAuth2 客户端不存在"是什么鬼**。这篇就把这套系统从前端视角梳理清楚，配我项目里的真实例子和踩过的坑。Kafka 单独有一篇《[消息队列与Kafka·前端视角](./消息队列与Kafka-前端视角)》，这里只讲它在本项目的位置。

---

  埋点是另一条异步线：
  浏览器 track() ──HTTP──▶ 埋点事件服务 ──Kafka──▶ 数仓消费 ──▶ StarRocks(ods.web_event)

复杂系统拆开就三类：**应用**（前端站/后台/后端）、**存储**（MySQL/Redis/StarRocks）、**中间件**（Nacos/Kafka/网关）。

## 1. Nacos —— 后端的"云端 .env"

### 一句话
Nacos 是**配置中心**（也能做服务注册，我们只用了配置能力，用的阿里云托管版 MSE）。

### 前端类比
就是**后端的 `.env`，但放在云端、集中管理、能热更新**。
- 前端：数据库地址/密钥写 `.env.production`，构建时打进包。
- 后端：这些**不写死在代码**，放 Nacos，应用启动去拉；改配置不用重新发版。

### 我们项目怎么用
一份后端代码要跑多产品 × 多环境，靠 Nacos 上按 `application-<产品>-<环境>.yaml` 分别存配置（DB、Redis、密钥、CDN 域名…）。启动时用环境变量说明身份：
```bash
-DPRODUCT_LINE=vibeshort -DNACOS_NAMESPACE=xxx
```
它就去拉对应那份配置。（我们只用配置、没开服务发现。）

### 你会在什么时候撞见它
后台"连错库 / 密钥不对 / 飞书 appId 配错 / 预发连到了测试库"——根基本都在 Nacos 那份 yaml。

## 2. Kafka —— 埋点数据的异步传送带（本项目位置）

原理详见《[消息队列与Kafka·前端视角](./消息队列与Kafka-前端视角)》。这里只说它在本项目干嘛：**埋点走 Kafka**。
```
前端 track()
  → HTTP 到埋点事件服务
  → 事件服务用 KafkaProducer 发到 Kafka topic   ← Kafka 在这
  → 数仓消费者消费
  → 落到 StarRocks 的 ods.web_event 表
```
为什么不直接写库：埋点量巨大、不能阻塞用户、下游不止一个。Kafka 当缓冲传送带——**异步、削峰、解耦**。前端只负责"发给事件服务"这一步，后面查不到就往这条链路排查。

## 3. 三个"存储"别搞混

| 名字 | 类型 | 干啥 | 前端类比 | 我们存什么 |
|---|---|---|---|---|
| **MySQL(RDS)** | 关系型(OLTP) | 业务增删改查+事务 | 正经"数据库" | 剧集、用户、CMS、菜单/字典/权限 |
| **Redis** | 内存KV/缓存 | 快、临时、热数据 | 服务端版 localStorage | 登录 token、缓存、限流计数 |
| **StarRocks** | 分析型(OLAP) | 海量明细聚合超快 | 专跑报表的大数据库 | 埋点明细 `ods.web_event` |

记：**业务功能→MySQL，缓存/token→Redis，查埋点/分析→StarRocks。**

> 查埋点小贴士：多产品共用一张 `web_event` 表，**必须按 `app_id` 区分**（VibeShort 是 `2616`），不加就串产品数据。

## 4. K8s 内网 Service vs 公网网关 —— 为什么两条路

- **K8s**：前端站/后台/后端都打成容器跑在集群 **pod** 里，每个环境(test/pre/prod)一套。
- **内网 Service**：集群内部用服务名互调，如 `http://aidrama-seo-api:8080`，走内网不出公网。
- **公网网关**：外部请求进集群要过网关，网关有**白名单**。

### 本项目最关键的坑
- **C 端是 SSR**：Next 在 **pod 内(服务端)** 调后端。公网 API 域名被网关白名单挡(**403**)，所以 C 端走**内网 Service** 直连后端，绕开网关。
- **后台是 SPA**：Vue 在**用户浏览器**里调后端，浏览器进不了内网，只能走**公网 API 域名**，靠后端开 **CORS** 解决跨域。

同一个后端，C 端和后台**走两条不同的路**——所以"C 端好的、后台报跨域"这种，要分开排查。（我就踩过：以为后台是跨域问题，最后发现是后端 503 + 数据没初始化。）

## 5. OAuth2 / Token —— 登录后那串"令牌"

yudao 登录会发一个 **access_token**，之后每个请求带着它证明身份。令牌由一个"OAuth2 客户端"签发，后台用内置的 `default`，这条记录存在数据库 `system_oauth2_client` 表里。
- **新环境漏导这条数据 → 登录报"OAuth2 客户端不存在"**（我们预发就踩了）。
- 类比：token = 门禁卡，每次刷；`default` 客户端 = 发卡机配置，发卡机没登记就发不出卡。

延伸：菜单、字典、角色、权限这些也都是数据库 `system_*` 表里的数据，**yudao 不会自动生成**，新环境部署要手动导 SQL——漏了就"后台空白/登录挂"。

## 6. 串起来：一次请求发生了什么

**A. 访客打开 C 端剧场页**
1. 浏览器 → 公网网关 → C 端 SSR(pod)
2. SSR 要数据 → 走**内网 Service** 调后端(app-api，加密)
3. 后端已从 **Nacos** 拉到配置 → 查 **MySQL**，热数据走 **Redis**
4. 返回渲染
5. 用户点击 → `track()` → 事件服务 → **Kafka** → 数仓 → **StarRocks**

**B. 运营登录后台**
1. 浏览器(SPA) → 网关 → 后台静态页
2. 飞书登录 → 浏览器走**公网 API 域名**调后端(admin-api，CORS)
3. 后端校验 → 用 `system_oauth2_client` 的 `default` 发 **token** → 存 **Redis**
4. 后续带 token 访问，菜单/字典/权限从 **MySQL** 的 `system_*` 表来

---

## 7. 一句话总结

- **Nacos** = 云端配置中心（连错库/密钥看它）
- **Kafka** = 埋点异步传送带（埋点查不到排查这条线）
- **MySQL/Redis/StarRocks** = 业务 / 缓存token / 埋点分析
- **内网 Service vs 公网网关** = C 端(SSR)走内网、后台(SPA)走公网，分开排查
- **OAuth2 `default` 客户端** = 后台登录发令牌的必备数据，新环境别漏导

作为前端，不用会搭这些中间件，但知道**每个东西在链路的哪一环、出问题该看哪**，排查效率就完全不一样了。
