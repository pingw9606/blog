# 从一行代码到线上容器 —— 前端视角的运维入门

> 背景：我是前端，最近自己搭了个 Node 服务（app-service：做客户端更新检查 + 用户统计 + 反馈），部署到了腾讯云。部署完我才发现，「代码写完」到「用户能访问」中间那一大段，全是我以前的盲区。这篇就把这段链路——**一行代码怎么变成服务器上一直跑着的容器、再变成公网能打开的地址**——从运维的角度拆开讲，全程用我这个真实的 app-service 当例子。
>
> 技术栈参照：一台腾讯云 Lighthouse（轻量服务器，Ubuntu）+ Docker + Node/Fastify 服务 + PostgreSQL。

---

## 0. 先扭转一个观念：服务器就是一台「一直开机、没有屏幕」的电脑

前端最容易把「服务器」想得很玄。其实它就是**一台装了 Linux、放在机房里、7×24 不关机、有公网 IP 的电脑**。区别只有两点：

- 没有显示器键盘，你通过 **SSH**（远程命令行）连上去操作：
  ```bash
  ssh ubuntu@124.223.111.221
  ```
- 它有个**公网 IP**，别人能通过网络访问它上面开放的端口。

你本地 Mac 能干的事它几乎都能干（跑 node、装数据库、开服务），只是全靠命令行。**把「部署」理解成「把代码搬到这台远程电脑上跑起来，并让外面能访问」**，整件事就不神秘了。

---

## 1. 三个核心概念：镜像、容器、Dockerfile

这三个词搞懂，Docker 就通了一大半。用前端熟悉的东西类比：

| Docker 概念 | 是什么 | 前端类比 |
|---|---|---|
| **Dockerfile** | 一份「怎么打包运行环境」的说明书 | `package.json` + 构建脚本 |
| **镜像（image）** | 按说明书打包好的**只读整包**（代码 + node + 依赖 + 系统库） | `npm run build` 产出的 `dist`，但连运行环境一起打包了 |
| **容器（container）** | 镜像**跑起来的一个实例**（活的进程） | `node dist/server.js` 真正在跑的那个进程 |

一句话串起来：**Dockerfile 是菜谱，镜像是预制菜，容器是端上桌那盘热的**。同一个镜像可以跑出多个容器，就像一份预制菜能热好几盘。

> 为什么前端要关心这个？因为它解决了你一定踩过的坑：「我本地能跑，到服务器就挂」。Docker 把「运行需要的一整套环境」连代码一起打包固定住，**换台机器也一模一样**。它之于服务器，约等于**锁死版本的 `node_modules` 之于项目**。

看下我 app-service 的 Dockerfile，很短，注释我加上了：

```dockerfile
FROM node:20-alpine        # 基础环境：一个内置了 Node 20 的极小 Linux
WORKDIR /app               # 容器内的工作目录
COPY package.json package-lock.json* ./
RUN npm install --omit=dev # 在镜像里装好生产依赖（打进包里）
COPY . .                   # 把代码拷进镜像
ENV NODE_ENV=production
EXPOSE 8090                # 声明这个服务用 8090 端口
CMD ["node", "src/server.js"]  # 容器启动时执行的命令
```

读这份文件，其实就是在读「这台服务要怎么从零跑起来」。

## 2. 完整链路：一行代码 → 公网可访问

这是本文的主线。以 app-service 为例，一次部署经过这几步：

```
   你的代码
      │  ① docker build（照 Dockerfile 打包）
      ▼
   镜像 image  ────────────────────────┐
      │  ② docker run（把镜像跑成容器）   │  可复用、可分发
      ▼                                 │
   容器 container（8090 在跑）           │
      │  ③ 端口映射 -p 8090:8090         │
      ▼
   宿主机（服务器）的 8090 端口
      │  ④ 云安全组放行 8090
      ▼
   公网：http://124.223.111.221:8090   ← 用户能打开了
```

逐段拆：

**① build：代码 → 镜像**
```bash
docker build -t app-service .
```
照着 Dockerfile 把「代码 + 环境」打包成一个镜像。

**② run：镜像 → 容器**
```bash
docker run -d app-service
```
`-d` 表示后台跑。这时候容器活了，8090 在**容器内部**监听——但外面还够不着。

**③ 端口映射：容器端口 → 宿主端口**
```bash
docker run -d -p 8090:8090 app-service
#                 ↑宿主  ↑容器
```
容器像一个封闭的盒子，`-p 宿主端口:容器端口` 相当于在盒子上开一个孔，把容器里的 8090 接到**服务器本机**的 8090。这一步做完，在服务器上 `curl localhost:8090` 就通了。

**④ 安全组放行：宿主端口 → 公网**
到这一步服务器自己能访问了，但公网还打不开。因为云厂商有一层**安全组（防火墙）**，默认只放行你允许的端口。要去腾讯云控制台加一条规则：**TCP 8090 允许**。

> 这就是我部署时卡住的地方：服务在服务器内部 `curl localhost:8090` 完全正常，但公网死活打不开——最后发现是安全组没放行 8090。**「本机通、公网不通」几乎总是安全组/防火墙问题**，这是运维排查的第一直觉。

## 3. docker compose：别再手敲一长串 run

真实项目容器不止一个，`docker run` 参数又臭又长。**compose 就是把这些参数写进一个 yaml 文件**，一条命令拉起来。我 app-service 的生产 compose（精简版）：

```yaml
services:
  app-service:
    build: .                    # 就地构建镜像
    env_file: .env              # 环境变量从 .env 读
    ports:
      - "8090:8090"             # = docker run 的 -p
    volumes:
      - ./uploads:/app/uploads  # 数据卷：容器里的文件存到宿主，删容器也不丢
    networks:
      - ouyang                  # 加入一个已存在的网络，才能连到数据库容器
    restart: unless-stopped     # 容器挂了自动拉起
networks:
  ouyang:
    external: true
    name: ouyang-app_default
```

之后部署/更新就一条命令：
```bash
docker compose -f docker-compose.prod.yml up -d --build
```

这里有两个**运维常识**前端要记住：

- **`volumes`（数据卷）**：容器是「用完即弃」的，删了重建里面的文件就没了。**要持久保存的东西（上传的文件、数据库数据）必须挂 volume 存到宿主机**。这也是为什么数据库容器删了数据还在。
- **`networks`（网络）**：容器默认互相隔离。我的 app-service 要连一个现成的 PostgreSQL 容器，就得**加入同一个 docker 网络**，然后用「容器名」当主机名连它（`postgres://...@ouyang-db:5432/...`）。容器之间靠**服务名**互相找，不用 IP。

## 4. 端口这件事：容器口 / 宿主口 / 安全组，三道门

前端最容易在这里懵。请求从公网打到你的代码，要穿过**三道门**：

```
公网请求 →【安全组】→ 服务器网卡 →【端口映射 -p】→ 容器 →【服务监听 EXPOSE】→ 你的代码
          云控制台配        宿主:容器           app 里 listen(8090)
```

任何一道门没开，都表现为「打不开」，但排查点完全不同：

| 现象 | 大概率是哪道门 | 怎么验证 |
|---|---|---|
| 服务器上 `curl localhost:8090` 就不通 | 容器没起 / 代码没 listen | `docker ps` 看容器在不在、`docker logs` 看报错 |
| 服务器本机通、**公网不通** | 安全组没放行 | 控制台加 TCP 规则；`ss -ltnp` 看是否 `0.0.0.0:8090` |
| 绑成了 `127.0.0.1:8090` | 端口映射只绑了本机 | compose 里改成 `8090:8090`（等于 `0.0.0.0`）|

> 补充一个安全细节：不是所有端口都该对公网开。我服务器上数据库(5432)、内部服务(8080/8000)都**只绑 `127.0.0.1`**，外面碰不到；只有对外的 web(80) 和 app-service(8090) 绑 `0.0.0.0`。**「内部服务只绑本机、对外服务才暴露端口」是基本安全姿势。**

## 5. 运维日常命令速查（这几条能覆盖 80% 场景）

```bash
# 看有哪些容器在跑、端口、状态
docker ps
docker ps --format "table {{.Names}}\t{{.Status}}\t{{.Ports}}"

# 看某容器日志（排查线上问题第一步）
docker logs app-service-app-service-1 --tail 50
docker logs -f xxx           # -f 实时跟

# 看资源占用（CPU/内存）
docker stats --no-stream

# 进容器内部（像 ssh 进一台小机器）
docker exec -it ouyang-db psql -U ouyang   # 直接进数据库

# 看服务器开放了哪些端口
ss -ltnp

# 看磁盘 / Docker 占用
df -h /
docker system df

# 更新部署（改完代码后）
docker compose -f docker-compose.prod.yml up -d --build
```

> 前端类比：`docker ps` ≈ 打开任务管理器看进程；`docker logs` ≈ 看 Console；`docker exec` ≈ 钻进那个进程的环境里敲命令。

## 6. 两种部署方式：手动 vs CI/CD

**方式一：手动（我 app-service 现在用的）**
```bash
# 本地改完 → 同步代码到服务器 → 在服务器上重建容器
rsync -az ./ ubuntu@服务器:~/app-service/
ssh ubuntu@服务器 'cd ~/app-service && docker compose -f docker-compose.prod.yml up -d --build'
```
简单直接，适合个人/内部项目。缺点：每次手动、构建占用线上机器 CPU。

**方式二：CI/CD（同机器上的欧阳项目用的）**
```
push 到 main
  → GitHub Actions 自动构建镜像
  → 推到镜像仓库（GHCR）
  → SSH 到服务器 pull 新镜像 + 重启
```
`git push` 即上线，构建在 CI 跑不占线上资源，能回滚（镜像有版本）。适合正式项目。

| | 手动 rsync+build | CI/CD + 镜像仓库 |
|---|---|---|
| 触发 | 手敲命令 | push 自动 |
| 构建在哪 | 线上机器（占资源）| CI 机器 |
| 回滚 | 麻烦 | 切镜像 tag 即可 |
| 适合 | 内部小服务 | 正式项目 |

## 7. 运维视角的「非功能」三件事：日志、备份、资源

功能跑通只是开始，**运维真正操心的是这三样**，也是前端最容易忽略的：

**① 日志**：出问题第一件事是看日志，不是改代码。`docker logs` 定位是 crash、连不上库、还是报错被吞。所以写服务时**关键节点要打日志**（启动成功、连库成功、请求失败原因）。

**② 备份**：数据库数据是**删了不可逆**的。容器可以随便重建，但库里的数据没了就没了。最低成本的做法是每天 `pg_dump` 导出 + 保留最近 N 天：
```bash
# 一条 cron 定时任务的核心
docker exec pg容器 pg_dump -U 用户 库名 > /backup/db-$(date +%F).sql
```
> 我这台目前**还没做自动备份**——这是当前性价比最高该补的事，比扩容重要得多。

**③ 资源与清理**：看一眼就知道机器还剩多少：
```
磁盘：40G 用了 15G（还剩 23G）
内存：3.3G，所有容器加起来才占几百 MB
```
资源够不够，取决于你放什么。轻服务（像 app-service 才占 21MB 内存）随便加；但要注意**磁盘会被慢慢吃掉**——比如发布的安装包、日志、旧镜像。定期 `docker image prune` 清理悬空镜像，历史文件设保留策略。

## 8. 线上服务打不开，按这个顺序查

一份可直接照做的排查动线（从外到内）：

1. **能 ping 通服务器吗** → 不通：机器挂了 / 网络问题。
2. **公网端口通吗**（`curl http://IP:端口/health`）→ 不通：先怀疑**安全组**。
3. **服务器本机通吗**（SSH 进去 `curl localhost:端口`）→ 不通：往里查容器。
4. **容器在跑吗**（`docker ps`）→ 不在：`docker logs` 看为什么退出。
5. **容器在跑但报错**（`docker logs`）→ 看是不是连不上数据库 / 环境变量缺失 / 代码异常。
6. **依赖服务正常吗**（数据库容器 healthy 吗、磁盘满没满 `df -h`）。

> 记住方向：**从外往里，一层层缩小**。「公网不通但本机通」→ 安全组；「本机也不通」→ 容器/代码；「容器在跑但 500」→ 日志 + 依赖。

## 9. 小结 & 前端↔运维 术语对照

一行代码上线，本质就是：**打包成镜像 → 跑成容器 → 映射端口 → 放行安全组 → 公网可达**，再叠上**日志、备份、资源**这三样长期运维。

留一张对照表，帮你把新词挂到已有认知上：

| 运维概念 | 前端已有的认知 |
|---|---|
| 服务器 | 一台一直开机、没屏幕、用 SSH 操作的电脑 |
| 镜像 image | 连运行环境一起打包的「dist」 |
| 容器 container | 真正在跑的那个进程实例 |
| Dockerfile | 打包说明书（≈ 构建脚本）|
| docker compose | 一键编排多个容器（≈ 一个 orchestrator 脚本）|
| 数据卷 volume | 容器的「持久化存储」，删容器不丢 |
| docker 网络 | 容器间用服务名互相访问的内网 |
| 端口映射 -p | 把容器端口接到服务器端口 |
| 安全组 | 云厂商的防火墙，控制公网能碰哪些端口 |
| CI/CD | push 自动构建+部署的流水线 |
| pg_dump | 数据库导出备份 |

前端转运维，不用一上来啃全套。抓住**「服务器=电脑、容器=隔离沙箱、镜像=打包环境、端口/安全组=几道门」**，再养成**「先看日志、记得备份、留意磁盘」**的习惯，就能把自己的服务稳稳跑在线上了。
