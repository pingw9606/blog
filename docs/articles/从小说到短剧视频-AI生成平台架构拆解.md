# 从小说到短剧视频：一个 AI 生成平台的架构拆解

> 一篇“能照着做”的架构学习笔记。以“小说/剧本 → 短剧视频”的一站式 AI 生成平台为例，拆解它的整体架构、端到端工作流，以及若干可迁移的工程实现：Agent 编排、AI 供应商抽象、剪映（CapCut）草稿协议、LLM 两阶段抽取等。
>
> 本文为通用技术研究笔记，不针对任何特定产品，示例结构与参数均为教学演示。

---

## 一、要解决的问题

目标是把“编剧 → 分镜 → 美术 → 视频 → 剪辑”这条重工业流水线，压成一个 Web 后台里的按钮流。用户丢进一段小说原文，平台依次完成：

```
上传小说/剧本
   → LLM 拆集（把长文切成一集集）
   → 元素推理（自动抽出 角色/场景/道具 及多状态）
   → 图片生成（角色三视图、九宫格关键帧）
   → 分镜策划（每集拆成分镜 + 镜头 + 转场 + 台词）
   → 提示词推理（分镜 → 可喂视频模型的提示词）
   → 视频生成（逐镜头出片）
   → 剪映导出（打包成可直接打开的剪辑草稿）
```

最终产物是一个**剪辑软件草稿工程**，创作者拿去做最后的人工微调。

## 三、整体架构

```
┌────────────────────────┐        ┌───────────────────────────────────┐
│      前端 (React)        │  HTTP  │             FastAPI                 │
│  项目/上传/风格/元素/分镜/ │ ─────▶ │  REST + Agent 编排入口               │
│  视频/预览/供应商/本地化   │ ◀───── │  JWT + OAuth + RBAC 权限守卫         │
└────────────────────────┘ JSON/SSE└───────────────┬───────────────────┘
                                                   │ 入队
                                    ┌──────────────▼──────────────┐
                                    │      Redis（Celery Broker）    │
                                    └──┬───────┬───────┬────────┬──┘
                              ┌────────▼┐ ┌────▼───┐ ┌─▼─────┐ ┌▼────────┐
                              │llm 队列  │ │image   │ │video  │ │export   │
                              │拆集/元素/ │ │(生图)   │ │(生视频)│ │(剪映导出)│
                              │分镜/提示  │ └───┬────┘ └──┬────┘ └───┬─────┘
                              └────┬─────┘     │         │          │
                        ┌─────────▼────────────▼─────────▼──────────▼────────┐
                        │  AI 适配器（工厂）: LLM / 图像 / 视频 多供应商可插拔     │
                        └─────────────────────┬──────────────────────────────┘
                        ┌──────────────┬───────▼────────┬──────────────┐
                        │   MySQL 8     │  对象存储(S3)    │  Redis 结果    │
                        └──────────────┴────────────────┴──────────────┘
```

一个值得学的编排选择：**应用层 / 中间件层分离**。用 docker-compose 只容器化“应用层”（api + 各 worker + 前端），MySQL / Redis / 对象存储复用外部既有实例（在环境变量里配地址）。本地开发因此不必背一堆中间件容器。

## 四、端到端工作流

整个平台围绕一个 **“项目”** 展开（一个项目 = 一部短剧），对应前端的一排 Tab：`上传 → 风格 → 元素 → 图片 → 拆集 → 分镜 → 视频 → 预览`。每一步都有对应的后端 Agent。

### 4.1 上传原文 & 设定风格
存原文；设定画风（预设/关键词）、画幅（默认 9:16 竖屏短剧）、分辨率、参考图。风格会贯穿后续所有生成。

### 4.2 元素推理 —— 两阶段 + 并发
从原文自动抽出**角色 / 场景 / 道具**，并为每个元素生成“基础态 + 多状态”。核心是**两阶段**：

- **阶段 1｜列清单**：让 LLM 输出全部元素的清单 + 原文线索（输出小，能覆盖全文不遗漏）。
- **阶段 2｜补详情**：把清单按 16 个/批切分，并发（信号量限流）调用，为每个元素生成多维度描述与多状态；单批失败重试、跨批互不影响。

> 为什么分两阶段？“一次让模型既列全又写细”会因输出过长而丢元素。**先用小输出保证完整性，再分批保证细节质量**——很实用的 LLM 工程手法。

### 4.3 拆集 —— 让代码做确定性的事
不让模型逐字摘录原文（贵且易错），只让它输出每集的**起止短句** + 标题概要；再由代码用短句在原文里**定位、切片**回填正文。

定位用了**“空白折叠 + 位置映射”的容错匹配**：把原文和短句里的连续空白/换行都折叠成单空格再查找，命中后映射回原文真实下标。这样即使模型输出的空白与原文不一致也能命中——省 token 又准确。

### 4.4 分镜策划
针对每一集生成“分镜 + 镜头”。要点：
- **元素以 id 引用**（而非名字），避免重名歧义；
- **默认负面约束**：视频里不得出现字幕条/台词叠加/水印/logo/BGM（画面内真实存在的招牌/手机 UI 文字属于场景内容，正常呈现）；
- **上集衔接**：从第 2 集起，把上一集概要/结尾场景/结尾镜头/收尾转场作为上下文，让本集开场自然承接；
- **转场**：分镜间转场类型，导出剪映时映射成内置转场。

### 4.5 图片生成 —— 分层提示词
生图提示词做**分层演进**以保证角色跨镜头一致：

1. **基础态**（人类可读的原文描述）；
2. **状态态**（继承基础态的“固有维度”，只覆盖变化项）；
3. 展开固有维度（时代/朝代/人种/性别/脸型/身材/头身比…）；
4. 拼成最终提示词：基础态强制 **16:9 三视图**（正/侧/背全身并排、特征一致、纯白背景、手部正常、禁止任何文字水印）。

除角色三视图，还有**九宫格关键帧**，给视频生成提供更细的画面锚点。

### 4.6 视频生成
按分镜逐镜头调用视频供应商，支持 `multi_ref`（多参考图）与 `first_last_frame`（首尾帧，做过渡/运镜很有用）两种模式。渠道可插拔。

## 五、关键实现：Agent 编排

平台的核心是一套 **Agent 编排**。每个步骤（拆集/元素/分镜）都不是“调一次 LLM 完事”，而是统一走一个 **“生成 → 校验 → 修正”循环**：

```
LLM 生成结果 → 用 validate_* 提示词校验 → 有问题就用 fix_* 提示词修正 → 直到通过或到重试上限
```

对应的提示词成对出现：`parse / validate / fix`。这套“自校验自修复”让 LLM 输出的结构化数据可靠性大幅提升。

每次运行是一个有状态的**会话（Session）**（running / completed / failed）。worker 启动时还有个**自愈机制**：自检把丢失/超时的“进行中”会话标记为 failed，避免僵尸会话拖住系统。

## 六、关键实现：剪映草稿协议（最硬核）

“生成一堆视频”不等于“交付一个可编辑的成片”。真正的价值落点，是把一组有序视频片段拼成**剪辑软件能直接打开的草稿工程**。草稿结构：

```
<draft_name>/
  draft_content.json      # 时间线主体
  draft_info.json         # 与 draft_content.json 完全相同（“双写”）
  draft_meta_info.json    # 素材清单 / 草稿元信息
  materials/video/*.mp4    # 实际视频文件
```

几个**决定“能不能打开”的关键细节**（踩坑血泪）：

1. **固定占位符 UUID**：素材路径用一个**写死的 UUID** 占位（如 `##_draftpath_placeholder_<固定UUID>_##`）。剪辑软件按这个固定值把草稿路径映射回本机草稿根目录再替换；**用随机 UUID 就认不出 → “媒体丢失”**。
2. **多处 material_id 必须一致**：每个素材 id 在 `materials.videos[]`、`segment.material_id`、`meta.draft_materials[]` 三处必须完全一致，否则关联不上媒体文件。
3. **所有空数组键都得在**：`materials` 里几十个空数组键（audios/texts/transitions…）一个都不能少，缺键可能被拒绝打开。
4. **版本对齐**：schema 需对齐目标软件的版本号。
5. **转场映射**：把抽象转场类型（叠化/闪白/闪黑/划像…）映射成内置转场的 `(effect_id, resource_id, 时长, is_overlap)`；转场挂在“前一个片段”上，最后一段无转场。

片段按 `target_timerange` 顺序累加拼接到单条视频轨。这段代码本质上是**逆向了剪辑软件的草稿格式**，是这类平台最有“干货”的部分。

## 七、关键实现：其它值得抄的设计

### 7.1 Celery 多队列：让不同 AI 任务互不阻塞
四类任务（文本 / 图片 / 视频 / 导出）用 `task_routes` 分流到独立 worker、各自设并发数。**如果不显式路由，所有任务会全落到默认队列，把生图/视频/导出全挤在一个 worker 上互相阻塞。**

```python
task_routes={
  "...agent_video_tasks.agent_export_jianying": {"queue": "export_queue"},
  "...agent_video_tasks.*": {"queue": "video_queue"},
  "...agent_image_tasks.*": {"queue": "image_queue"},
  "...agent_llm_tasks.*":   {"queue": "llm_queue"},
}
```

### 7.2 AI 适配器：工厂模式 + 数据库配置
用工厂 + 统一接口封装各供应商，**把供应商配置存进数据库**（按 text/image/video 能力区分，可在后台动态启用/切换）。换模型、加渠道不用改代码，配置即生效。

### 7.3 独立能力服务 + 零依赖 CLI
- 对只有命令行的能力（如某视频引擎），用一个**独立小服务**把它包成 HTTP API（提交 / 查状态 / 返回成片 URL），让主后端可标准化调用。
- 另配一个**零第三方依赖**（仅 Node 18+ 内置 `fetch`）的 CLI，支持登录、列渠道、直连视频渠道生视频（多模态参考、首尾帧、幂等键）与通用透传，方便自动化与调试。

## 八、如何跑起来（通用步骤）

1. **配置环境变量**：数据库 URL、Redis URL、JWT 密钥、各 AI 供应商 Key、对象存储配置。
2. **初始化数据库**：建表脚本 + 初始化数据（RBAC 角色权限、各供应商）。
3. **启动应用层**：`docker compose up -d --build` 起 api + 各 Celery worker + 前端；中间件复用外部实例。
4. **访问**：前端页面 + `/docs`（FastAPI 文档）+ `/api/health` 健康检查。
5. **裸跑调试**：`uvicorn app.main:app --reload` + 各队列各起一个 `celery ... worker -Q <queue>`。

## 九、可迁移的工程经验（重点）

1. **LLM 两阶段抽取**（先小输出列全，再分批补细）解决“又要全又要细”的矛盾。
2. **生成→校验→修正循环**：让不可靠的 LLM 输出变可靠，成对提示词 + 重试上限。
3. **让代码做确定性的事**：模型只给“起止短句”，切片交给代码（容错匹配），既省 token 又准确。
4. **多队列隔离**不同耗时/资源画像的任务，避免长任务饿死短任务。
5. **供应商配置进数据库**：AI 渠道即插即用，换模型零改码。
6. **分层提示词**：固有维度继承 + 状态覆盖 + 最终拼装，保证角色跨镜头一致性。
7. **逆向剪辑草稿协议**：固定占位 UUID、多处 id 对齐、补齐空键、版本对齐，把“生成视频”落到“可编辑成片工程”。
8. **应用层/中间件层分离**的编排，降低本地开发负担。
9. **自愈机制**：worker 启动自检清理僵尸会话，提升长期可用性。
