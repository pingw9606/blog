# 数据到底存在哪台机器、怎么存的 —— 前端视角读懂 DMS 里的数据库实例

> 背景：我在 DMS 里查埋点，左边一拉出来几十个"实例"——`prod-aidrama`、`xxx-redis`、`阿里云starrocks`、`大数据从库`……看得一脸懵：**这些表到底在哪、在哪台机器、以什么方式存的？** 作为前端，平时只管调接口，数据落在哪从来是黑盒。这篇就把这套东西讲清楚，让你以后**看一眼 DMS 就知道某张表在哪、什么引擎、怎么存**。

---

## 0. 先破一个概念：表不是"文件"

你在 DMS 里看到的表，**不是躺在某个文件夹里的文件**。它是**某一台（或一组）数据库服务器**内部管理的数据结构，物理上存在那台服务器的磁盘/内存里、由数据库引擎自己管。你**不用关心它的物理文件在哪**——连上那台服务器、用 SQL 查就行。

这跟前端不一样：前端的资源是实实在在的文件（.js/.png 放 CDN）；数据库的"表"是**逻辑结构**，物理存储被引擎封装了。

## 1. DMS 是什么：一个"统一的数据库客户端"

DMS（阿里云 Data Management）≈ **数据库版的统一后台 / Postman**。它本身**不存数据**，只是帮你用一个网页界面**连上背后几十个真实的数据库服务器**。

你左边看到的"免登录实例（32）"——**每一个「实例」就是一台/一组真实的数据库服务**，各有自己的：
- **地址**（`host:端口`）—— 它在哪台机器/内网；
- **引擎类型**（MySQL / Redis / StarRocks…）—— 它以什么方式存；
- **库 → 表** —— 逻辑归属。

所以"32 个实例"= 32 个不同的数据库服务（不同机器、不同类型、不同产品线），DMS 只是把它们聚在一个界面里。

## 2. 三类存储 = 三种机器 + 三种存法

| DMS 里的实例（举例） | 引擎 | 跑在哪 | 怎么存 | 存什么 |
|---|---|---|---|---|
| `prod-aidrama`、`prod-storyreel` | **MySQL / RDS** | 阿里云托管的 RDS 服务器 | **行存**（一行行存，适合按主键增删改查单条） | 业务数据：用户、剧集、订单、CMS |
| `xxx-redis`、`center-prod-redis` | **Redis** | Redis 实例（内存型） | **内存 KV**（放内存，快，有持久化兜底） | 缓存、登录 token、限流计数 |
| `阿里云starrocks`（查埋点那个） | **StarRocks** | StarRocks **集群**（多节点 MPP） | **列存**（按列存，适合海量数据聚合分析） | 埋点明细 `ods.web_event`、行为/大数据 |
| `xxx-大数据从库`、`DTS 同步` | 从库 / 同步管道 | 各自机器 | 主库的**同步副本** | 供分析读，不拖累业务主库 |

一句话对应：**业务功能找 MySQL，缓存/token 找 Redis，查埋点/跑分析找 StarRocks。**

## 3. 怎么自己"看出"一张表在哪、怎么存

在 DMS 里就盯两处信息：

### ① 连接地址 `host:端口` —— 它在哪台机器
比如查埋点时地址栏是 `ods@10.70.0.8:9030`：
- `10.70.0.8` 是**内网 IP** → 这库跑在内网某台机器/集群；
- `9030` 是 **StarRocks 的端口** → 引擎是 StarRocks。

### ② 端口/图标 —— 判断引擎（怎么存）
**看端口基本就能猜引擎**：

| 端口 | 引擎 | 存储方式 |
|---|---|---|
| 3306 | MySQL | 行存（OLTP） |
| 6379 | Redis | 内存 KV |
| 9030 | StarRocks | 列存（OLAP/MPP） |
| 5432 | PostgreSQL | 行存 |

DMS 每个实例前的**图标 / 详情里的"数据库类型"**也直接标了引擎。

## 4. 一张心智图

```
你(浏览器) → DMS 统一管理台（只是客户端，不存数据）
                 │  连接到多个「实例」(每个=一台/组真实DB服务器, 有 IP:端口)
                 ├── RDS MySQL(prod-aidrama…)   → 业务数据 · 行存 · 3306
                 ├── Redis(xxx-redis)           → 缓存/token · 内存 · 6379
                 ├── StarRocks(10.70.0.8:9030)  → 埋点/分析 · 列存 · 9030 · MPP集群
                 └── 大数据从库/DTS              → 主库的同步副本 · 供分析
```

## 5. 顺带理解"为什么要分这么多"

- **业务库和分析库分开**：业务 MySQL 要支撑用户实时增删改查（OLTP），埋点/报表是海量数据聚合（OLAP），两种负载特性完全不同，硬塞一起会互相拖垮。所以埋点单独放 StarRocks。
- **从库/DTS**：直接在业务主库上跑大查询会影响线上，所以同步一份到从库/数仓专门给分析用。
- **按产品线拆实例**：`prod-aidrama` / `prod-storyreel` 各一套库，数据隔离、互不影响（上线时"库隔离"就是在说这个）。

## 6. 一句话总结

- **表 = 某台数据库服务器里的逻辑结构**，物理存储引擎自己管，你只管连上去用 SQL 查。
- **DMS = 统一客户端**，里面每个「实例」是一台/组真实 DB 服务（有 `IP:端口` + 引擎类型 + 库表）。
- **看连接地址判断在哪台机器/内网，看端口/引擎类型判断怎么存**（3306 MySQL 行存跑业务、6379 Redis 内存做缓存、9030 StarRocks 列存做分析）。

下次在 DMS 里再看到一堆实例，别慌——**先看它的 `host:端口` 和引擎**，就知道这张表在哪、是什么、怎么存的了。
