# 灰度发布 —— 前端视角：为什么"部署成功了"线上还是老样子

> 背景：这次给埋点服务加一条 CORS 白名单，我盯着排查——代码合进 master 了、部署平台显示"成功"了、时间也对（部署晚于代码合并），可线上实测就是没生效，接口一直被拦。折腾半天，运维一句话点破："**在灰度，没全量**"。这篇就把"灰度发布"从前端视角讲清楚：它是什么、为什么要有它、以及它会给排查埋下什么坑——这个坑我这次实打实踩了。

---

## 0. 先看我踩的这个坑（真实场景）

需求很简单：让埋点服务允许新站点的域名跨域上报（加一条 CORS 白名单）。流程都走完了：

- ✅ 代码改好、MR 合并进 `master`（昨天就合了）
- ✅ 部署平台点了发布，状态**「成功」**（今天上午，比代码合并还晚）
- ❌ 但线上实测：接口**还是老行为**，白名单没生效，一直报错

我一度怀疑是 DNS、证书、CNAME、甚至代码没合对……查了一圈全是对的。最后真相是：**这次部署是「灰度」的——只更新了一部分实例/放了一部分流量，大部分请求还是打到了没更新的老实例上**。运维点了「全量」之后，秒通。

**"部署成功" ≠ "全量生效"** —— 这就是灰度带给排查的最大迷惑。

---

## 1. 什么是灰度发布

灰度发布（也叫**金丝雀发布 / Canary Release**）：**新版本上线时，不一次性替换全部，而是先放给一小部分（比如 5%、一台实例、某个地区的用户），观察没问题，再逐步扩大到 100%。**

名字来源：矿工下矿带只金丝雀，毒气超标金丝雀先出事——用"小代价的先行者"探路。灰度里那"一小部分流量"就是金丝雀。

## 2. 前端其实早就见过它的"表亲"

- **功能开关 / AB 测试**：新功能先开给 1% 用户，看数据再放量——这是**功能层**的灰度。
- **灰度部署**：则是**部署层**的灰度，同一个服务同时跑着**新旧两个版本**，按比例分流量。

一句话：**"先给一小撮试，没问题再铺开"**，前端后端都在用，只是层次不同。

## 3. 为什么要灰度（不直接全量）

- **控制爆炸半径**：新版本有 bug，也只影响一小部分流量/用户，不会全站崩。
- **可快速回滚**：发现问题，把那点流量切回老版本即可，代价极小。
- **真实环境验证**：预发再像也不是生产，灰度用少量真实流量验证最稳。

所以灰度是**好东西**——它是拿"发版风险"换"可控性"。只是……

## 4. 灰度给排查埋的坑（前端必知）

灰度期间，**新旧版本同时在线**，于是会出现这些迷惑现象：

- **"部署成功"了，但线上行为没变**（我这次）——因为你的请求大概率打到了还没更新的老实例。
- **时好时坏、时通时不通**——同一个域名/接口，刷几次一会儿正常一会儿报错。因为负载均衡把你的请求**轮询**到了新/旧不同实例。
- **"我本地/某台测是好的，别人说不行"**——你俩的请求打到了不同版本的实例。

> ⚠️ 关键认知：一个域名背后往往是**多台实例**（我这次 `event.xxx` 就解析到两台 EC2）。灰度时它们**版本不一致**，你看到的结果取决于这次请求落到哪台。

## 5. 前端怎么排查"疑似灰度"的问题

1. **多打几次看抖动**：同一个请求连发 5~10 次，如果**时好时坏**，基本就是灰度中（新旧实例并存）。稳定全好/全坏才是全量状态。
   ```bash
   for i in $(seq 1 6); do curl -s -o /dev/null -w "%{http_code}\n" <接口>; done
   # 结果 200/403/200/403… 交替 → 灰度中；全 403 → 还没滚到；全 200 → 全量好了
   ```
2. **按实例/IP 分别测**：绕过负载均衡，直接打每台实例，确认哪些更新了、哪些没有。
   ```bash
   curl --resolve 域名:443:<实例IP> https://域名/...   # 逐台点名
   ```
   我这次就是这么发现"两台 EC2 都还没更新"，从而判断全量还没滚到。
3. **确认「全量完成」再下结论**：别在灰度中间就断言"没生效/代码有问题"。先问一句"是不是灰度、全量了吗"，能省一小时。
4. **看部署平台的灰度状态**：多数平台会显示"灰度 X% / 全量"，别只看到"成功"就以为全量了。

## 6. 顺带认识几个相关词

- **蓝绿发布**：准备两套完整环境（蓝=旧、绿=新），一键把流量整体从蓝切到绿，出问题再切回。和灰度的区别：蓝绿是"整体切换"，灰度是"逐步放量"。
- **全量**：灰度的终点——所有实例/流量都换成新版本。
- **回滚**：把流量/版本切回上一个好版本。灰度天然好回滚（切走那点流量即可）。

## 7. 一句话总结

- **灰度 = 新版本先放一小部分、验证没问题再逐步全量**，为了控风险、好回滚。
- 代价是**灰度期间新旧并存**，会让人误判：**"部署成功"不等于"全量生效"**，接口可能**时通时不通**。
- 前端排查三板斧：**多打看抖动 → 按实例点名 → 确认全量了没**。遇到"改了、部署成功了却没生效"，先怀疑灰度，别急着怀疑代码。

这次埋点的坑，本质就是**我拿"全量"的预期去验证一个"灰度中"的状态**——认知对上了，问题一秒就清楚了。
