# 03 · 上传队列引擎：断点续传 + 自动重试 + 并发控制

> 这是整个项目最核心、最值得学的一篇。目标：**关软件、断网、失败都不丢进度**。本篇一步步拆 `src/main/scheduler/queue.ts` 的完整实现——任务模型、并发调度、断点续传、失败归类与退避重试、网络挂起自动恢复、暂停/继续、启动恢复。

## 一、整体设计

上传是个"生产者-消费者"模型：

- **生产者**：用户提交一批文件 → 先注册到 CMS → 落库为 `pending` 任务。
- **消费者**：`kick()` 驱动，按并发数从 `pending` 里取任务执行 `runOne`。
- **状态机**：`pending → uploading → success / failed / paused`，任何异常都要落到一个明确状态。
- **持久化**：任务列表写本地文件（`task-store`），断点信息由七牛 SDK 写 `.ckpt` 文件。关软件重开能接着传。

```
submitDramaBatch(注册+入库pending) ──▶ kick() ──并发──▶ runOne(task)
                                                          │
                        ┌─────────────────────────────────┼──────────────────────────┐
                        ▼                 ▼                ▼               ▼
                     success           network          retryable       不可重试/超限
                   清ckpt+通知+测速   挂起队列探测恢复   退避后重入队      终态failed+上报
```

## 二、任务模型与常量

```ts
const MAX_RETRY = 3
// 自动重试退避（毫秒）：第 1/2/3 次
const BACKOFF = [2000, 8000, 30000]

// 断点续传文件目录：每个任务一个 .ckpt，SDK 记录已上传分片
const checkpointDir = join(app.getPath('userData'), 'checkpoints')
function checkpointPath(taskId: string) {
  return join(checkpointDir, `${taskId}.ckpt`)
}
```

任务类型（`shared/types.ts`）关键字段：`status`、`percent`、`retryCount`、`nextAttemptAt`（退避后可再执行的时间戳）、`fileUUID`（决定七牛存储 key）。

## 三、并发调度：kick()

`kick()` 是队列的心脏——**尽量补满 N 个并发**（N 用户可调）：

```ts
let active = 0

export function kick() {
  if (networkPaused) return                 // 网络挂起期间不启动新上传
  const concurrency = getConcurrency()      // 用户设置的并发数
  while (active < concurrency) {
    const task = nextPending()
    if (!task) break
    active++
    update(task.id, { status: 'uploading' })  // 注意：不重置 percent（续传要保留进度）
    void runOne(task).finally(() => {
      cancelSources.delete(task.id)
      active--
      kick()                                // 一个传完，立刻补下一个
    })
  }
}

// 取下一个可执行的 pending（跳过还在退避窗口内的重试任务）
function nextPending(): UploadTask | undefined {
  const now = Date.now()
  return store.getTasks().find(
    (t) => t.status === 'pending' && (!t.nextAttemptAt || t.nextAttemptAt <= now),
  )
}
```

- `active` 记录当前在传数量，`while (active < concurrency)` 补满。
- 每个任务 `.finally` 里 `active--` 再 `kick()`——形成"传完一个立刻补一个"的流水线。
- `nextPending` 跳过 `nextAttemptAt` 还没到的任务，这是退避重试的关键（下面讲）。

## 四、单个任务：runOne

```ts
async function runOne(task: UploadTask) {
  // ① 上传前预检：源文件可能已被移动/删除（不可重试）
  if (!existsSync(task.filePath)) {
    clearCheckpoint(task.id)
    update(task.id, { status: 'failed', percent: 0, errorMessage: '源文件不存在或已被移动/删除，请重新导入后上传' })
    return
  }
  try {
    const source: QiniuCancelToken = { cancelled: false }
    cancelSources.set(task.id, source)     // 存取消令牌，暂停时用

    // ② 存储 key = hls/{fileUUID}.{ext}，与注册时对齐
    const ext = task.fileName.includes('.') ? task.fileName.split('.').pop() : 'mp4'
    const storeKey = `hls/${task.fileUUID}.${ext}`

    // ③ 按 key 申请七牛上传 token（token 内置 callbackUrl，传完七牛回调 CMS 触发转码）
    const [token] = await getQiNiuTokenList([storeKey])
    if (!token) throw new Error('获取七牛上传 Token 失败')

    // ④ 上传（带进度回调 + 断点文件 + 取消令牌）
    let lastPercent = -1
    const uploadStartAt = Date.now()
    await uploadToQiniu(task.filePath, token, storeKey, (percent) => {
      // 守卫：任务若已被暂停/移除，停止回写进度（避免在途分片传完后把状态刷回 uploading）
      const cur = store.getTask(task.id)
      if (!cur || (cur.status !== 'uploading' && cur.status !== 'pending')) return
      const p = Math.round(percent * 100)
      if (p === lastPercent) return          // 百分比没变就跳过，避免高频写盘
      lastPercent = p
      update(task.id, { status: 'uploading', percent: p })
    }, checkpointPath(task.id), source)

    // ⑤ 成功：埋点 + 清断点文件 + 完成通知 + 测速上报
    await ttUploadJsSuccessLog(task.fileUUID!)
    clearCheckpoint(task.id)
    update(task.id, { status: 'success', percent: 100, errorMessage: undefined })
    maybeNotifyBatchComplete(task.shortPlayCode, task.shortPlayName)
    // ...测速上报（见第五篇）
  } catch (err: any) {
    // ⑥ 异常处理（暂停 / 网络 / 重试 / 终态失败）——下面详解
  }
}
```

进度回调里两个工程细节值得学：

1. **状态守卫**：暂停/移除任务后，可能还有"在途分片"传完触发回调。如果不加守卫，会把已经 `paused` 的任务状态刷回 `uploading`。所以每次回调先查当前状态，不对就直接 return。
2. **百分比节流**：`if (p === lastPercent) return`。上传进度回调触发极频繁，每次都写盘 + IPC 会很费。只在整数百分比变化时才更新。

## 五、断点续传：靠七牛 SDK 的 record 文件

断点续传不用自己实现，七牛 Node SDK 的 `ResumeUploader` 支持——关键是给它一个**固定的 record 文件路径**，它会把"已上传哪些分片"记在里面，中断后传同一路径就自动续传：

```ts
// src/main/uploader/qiniu.ts
export async function uploadToQiniu(filePath, token, key, onProgress, recordPath?, cancelToken?) {
  const config = new qiniu.conf.Config()
  config.useHttpsDomain = true

  const resumeUploader = new qiniu.resume_up.ResumeUploader(config)
  const putExtra = new qiniu.resume_up.PutExtra()
  putExtra.version = 'v2'                            // 分片上传 v2
  if (recordPath) putExtra.resumeRecordFile = recordPath  // ★ 断点续传记录文件

  // 进度回调；若已取消则抛特殊错误中止本次上传
  putExtra.progressCallback = (uploadedBytes, totalBytes) => {
    if (cancelToken?.cancelled) throw new Error(QINIU_CANCELLED)
    if (totalBytes > 0) onProgress(uploadedBytes / totalBytes)
  }

  await new Promise<void>((resolve, reject) => {
    resumeUploader.putFile(token, key, filePath, putExtra, (err, body, info) => {
      if (err) return reject(err)
      if (info?.statusCode === 200) resolve()
      else reject(new Error(`七牛上传失败 status=${info?.statusCode}`))
    })
  })
}
```

- `resumeRecordFile` 指向 `userData/checkpoints/{taskId}.ckpt`——**每个任务独立**，续传时 SDK 读它跳过已传分片。
- **成功后要 `clearCheckpoint` 删掉**，否则残留文件会占空间、也可能影响同 key 重传。
- 七牛 Node SDK 没有显式 `abort`，所以"取消"是通过**在进度回调里抛错**来尽力中止的（`cancelToken.cancelled` 置 true → 下次回调抛 `__CANCELLED__`）。断点文件保留，下次可续。

## 六、失败归类：classifyError

不同失败要区别对待——文件没了没救、凭证过期能重试、断网要挂起等恢复、4xx 是业务问题不该重试。这个归类函数是"体验好不好"的关键：

```ts
function classifyError(err): { message: string; retryable: boolean; category: string } {
  const raw = String(err?.message ?? '')
  const code = String(err?.code ?? '')
  const status = err?.response?.status ?? err?.statusCode  // 兼容 axios 与七牛

  // 本地文件问题：不可重试，需重新导入
  if (code === 'ENOENT' || /ENOENT|no such file|不存在/i.test(raw))
    return { message: '源文件不存在或已被移动/删除，请重新导入后上传', retryable: false, category: 'file' }

  // 凭证失效：可重试（重试会重新申请 token）
  if (/token|凭证|鉴权|credential|expired|过期/i.test(raw))
    return { message: '上传凭证失效，正在重新获取并重试', retryable: true, category: 'token' }

  // 网络类：交给网络挂起逻辑（不消耗重试次数）
  if (['ECONNABORTED','ETIMEDOUT','ENOTFOUND','ECONNREFUSED','ECONNRESET','EAI_AGAIN'].includes(code)
      || /timeout|network|socket|ECONN|超时|网络|连接/i.test(raw))
    return { message: '网络异常，网络恢复后会自动继续', retryable: true, category: 'network' }

  // 5xx：暂时性，可重试
  if (typeof status === 'number' && status >= 500)
    return { message: `服务暂时不可用（${status}），稍后自动重试`, retryable: true, category: 'server' }

  // 4xx：业务校验失败（集数冲突/命名不符），需人工，不自动重试
  if (typeof status === 'number' && status >= 400)
    return { message: `上传被拒绝（${status}）：${raw || '请检查文件名与集数后重试'}`, retryable: false, category: 'client' }

  // 兜底：按可重试处理，避免漏掉瞬时错误
  return { message: raw || '上传失败', retryable: true, category: 'unknown' }
}
```

## 七、catch 里的四条分支

```ts
} catch (err: any) {
  // ① 主动暂停导致的中止：保留断点与进度，置 paused，不重试不计失败
  if (pausingIds.has(task.id) || err?.message === QINIU_CANCELLED) {
    pausingIds.delete(task.id)
    const t = store.getTask(task.id)
    update(task.id, { status: 'paused', percent: t?.percent ?? 0 })
    return
  }

  const { message, retryable, category } = classifyError(err)

  // ② 网络错误：不消耗重试次数，挂起队列等网络恢复
  if (category === 'network') {
    update(task.id, { status: 'pending', percent: 0, errorMessage: '网络中断，已暂停，恢复后自动继续' })
    enterNetworkPause()
    return
  }

  const retryCount = task.retryCount ?? 0
  // ③ 可重试且没超上限：退避后自动重试
  if (retryable && retryCount < MAX_RETRY) {
    const delay = BACKOFF[retryCount] ?? 30000
    update(task.id, {
      status: 'pending',
      retryCount: retryCount + 1,
      nextAttemptAt: Date.now() + delay,       // ★ 关键：设定下次可执行时间
      errorMessage: `${message}（${Math.round(delay/1000)}s 后第 ${retryCount+1} 次重试）`,
    })
    setTimeout(kick, delay + 50)               // 退避时间到后再驱动
  } else {
    // ④ 不可重试或超上限：终态失败，清断点，上报
    clearCheckpoint(task.id)
    const suffix = retryable ? `（已自动重试 ${retryCount} 次仍失败，可手动重试）` : ''
    update(task.id, { status: 'failed', percent: 0, errorMessage: `${message}${suffix}` })
    void reportError('upload', `上传失败 ${task.fileName} [${category}] ${message}`, err?.stack)
  }
}
```

退避重试的机制串起来看：任务置回 `pending` 但设 `nextAttemptAt = now + delay`，`nextPending()` 会跳过还没到时间的任务，`setTimeout(kick, delay)` 到点再驱动——**用状态 + 时间戳实现"延迟重入队"，不阻塞其他任务**。

## 八、网络挂起与自动恢复

断网时不该一个个任务去重试（浪费次数、刷屏），而是**整个队列挂起，探测到网络恢复再统一继续**：

```ts
let networkPaused = false
let probeTimer = null

async function isOnline(): Promise<boolean> {
  try {
    await axios.head(config.apiBase, { timeout: 4000 })
    return true
  } catch (e) {
    return Boolean(e?.response)  // 有响应（含 4xx/5xx）就说明网络通了
  }
}

function enterNetworkPause() {
  if (networkPaused) return
  networkPaused = true
  probeTimer = setInterval(async () => {
    if (await isOnline()) {
      networkPaused = false
      clearInterval(probeTimer); probeTimer = null
      kick()                     // 网络回来了，继续
    }
  }, 5000)
}
```

`isOnline` 有个小技巧：只要 `axios.head` 拿到**任意 HTTP 响应**（哪怕 404/500）就算网络通——因为我们探测的是"网络连通性"，不是"接口正确性"。`kick()` 开头也有 `if (networkPaused) return`，挂起期间不启动新任务。

## 九、暂停 / 继续 / 手动重试

```ts
export function pauseTask(id: string) {
  const t = store.getTask(id)
  if (t?.status === 'uploading') {
    pausingIds.add(id)
    const src = cancelSources.get(id)
    if (src) src.cancelled = true          // 触发取消，runOne catch 置 paused
  } else if (t?.status === 'pending') {
    update(id, { status: 'paused' })
  }
}

export function resumeTask(id: string) {
  const t = store.getTask(id)
  if (t?.status !== 'paused') return
  update(id, { status: 'pending', nextAttemptAt: undefined })  // 重入队，从断点续传
  kick()
}

export function retryTask(id: string) {
  const t = store.getTask(id)
  if (!t || t.status === 'uploading') return
  update(id, { status: 'pending', percent: 0, retryCount: 0, nextAttemptAt: undefined, errorMessage: undefined })
  kick()  // 重置重试次数，重新开始
}
```

## 十、启动恢复：关软件也不丢

应用启动（登录后）会调 `recoverOnStartup`——把上次异常中断（还是 `uploading`）的任务重置为 `pending`，靠断点文件从中断处续传：

```ts
export function recoverOnStartup() {
  const tasks = store.loadTasks()          // 从磁盘读回任务列表
  for (const t of tasks) {
    if (t.status === 'uploading' || t.status === 'paused') {
      // 保留已持久化的 percent：重开进度条立即显示上次位置，不回跳 0
      store.updateTask(t.id, { status: 'pending', nextAttemptAt: undefined })
    }
  }
  kick()
}
```

因为任务列表落了盘、断点信息也落了盘，所以"关软件 → 重开 → 自动接着传"这个体验就成立了。

## 小结

这套队列的可靠性来自几个配合：

- **并发调度**：`kick()` + `active` 计数 + `.finally` 回补，流水线不空转。
- **断点续传**：七牛 `resumeRecordFile` + 每任务独立 `.ckpt`，成功即清。
- **失败分级**：`classifyError` 把错误分成"文件/凭证/网络/5xx/4xx/未知"，决定重试与否和话术。
- **退避重试**：`status=pending + nextAttemptAt` + `setTimeout(kick)`，不阻塞其他任务。
- **网络挂起**：断网整队挂起、探测恢复再继续，不消耗重试次数。
- **持久化 + 启动恢复**：任务和断点都落盘，关软件重开接着传。
