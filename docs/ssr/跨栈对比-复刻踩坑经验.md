# 跨栈对比·收官篇：复刻踩坑与经验

> 把 Nuxt 3 老站复刻成 Next 16 新站，真正动手时会踩哪些坑。这篇是整个「SSR 项目实战」系列的收尾，把前面各篇的迁移要点汇成一份**可对照的清单**。

---

## 1. 状态管理：别把 Pinia 照搬成全局 store

- **老站**：数据、筛选态都塞 Pinia 全局共享。
- **坑**：直觉是"找个 React 全局 store（Zustand/Context）一比一翻译"。
- **正解**：能在 **Server Component 取好数据直接传 props** 的，就别进全局态；只有真正的客户端交互态（翻页、开关、播放进度）才用 `useState`。
- 例：`dramaStore` 的"列表+当前页" → 页面服务端取 `initialData` 传 `DramasClient`，翻页态才客户端 `useState`。

## 2. 取数：composable → Server Component + lib/api

- `useApi().request()` / `useAsyncData` → **Server Component 里 `await lib/api`**。
- **server-only 边界**：加解密、密钥只能在服务端；客户端组件**只能 `import type`** 引用 `lib/api`，运行时引入会把密钥打进浏览器包。
- 客户端要数据 → 走 `app/api/*/route.ts`（route handler），别把 server-only 逻辑塞进 `"use client"`。

## 3. 组件边界：Vue 同构 → RSC / "use client"

- **老站**：组件默认两端跑，`import.meta.client` / `<ClientOnly>` 区分。
- **新站**：默认是 **Server Component**（只在服务端）；用到 `useState`/`useEffect`/事件/浏览器 API 才加 `"use client"`。
- **坑**：习惯性给所有组件加 `"use client"` → 丢掉 RSC 的好处（首屏小、密钥安全）。原则：**能不加就不加，交互叶子节点才加**。

## 4. 渲染模式：读请求头会"变动态"

- **坑**：详情页随手读了 `host`（`headers()`）→ 页面被强制 `force-dynamic`，与想要的 ISR 冲突，甚至构建/运行报错（真实踩过详情页 500）。
- **正解**：想清楚每个页面要 SSG / ISR / SSR；要读请求上下文就明确 `force-dynamic`，别又想 ISR 又读 host。

## 5. 构建不能强依赖后端

- **坑**：build 时调后端，后端 403/503 → 构建失败。
- **正解**：数据层**失败回退 mock/静态兜底**（如 `getLanguages()` catch 回退 `staticLanguages()`），保证"后端挂了也能构建、能渲染"。

## 6. i18n：语言包能平移，调用要改

- **能平移**：`locales/*.json` → `messages/*.json`（key 结构基本一致）。
- **要改**：`$t` → `getTranslations`(服务端)/`useTranslations`(客户端)；`localePath`/`<NuxtLink>` → `@/i18n/navigation` 的 `Link`。
- **要对齐**：locale 列表（老站 19 → 新站 16），hreflang/sitemap 跟着改。

## 7. 样式：scoped / Less-Sass → CSS/SCSS Modules

- Vue `<style scoped>` → **SCSS Modules**（`*.module.scss` + `styles.xxx`）。
- 颜色/断点等沉淀为 CSS 变量 / tokens，别散落魔法值（新站约定 C 端禁 Tailwind、统一 SCSS Modules）。

## 8. 自动导入 → 手动 import

- Nuxt 自动导入 components/composables/utils/stores；**Next 全部手动 import**。迁移时最琐碎但机械的一步。

## 9. 路由：pages:extend 正则 → catch-all + 代码解析

- 老站用 `pages:extend` 正则 + `middleware/redirect-*-page-1` 精控 SEO URL。
- 新站用 `[[...slugs]]` catch-all + 代码里 `parseSlugs` 区分"数字分页 / slug 详情"，重定向在代码里判断。

## 10. 播放器：xgplayer → hls.js 重写（解密插件复用）

- 脱掉 xgplayer 成品壳，直接用 `hls.js` + 自封装 UI；
- **加密 HLS 的 `hls-decryts-plugin` 两站共用**，不用重造解密逻辑。

---

## 迁移速查清单

| 老站（Nuxt 3） | 新站（Next 16） | 迁移动作 |
|---|---|---|
| Pinia 全局态 | 服务端取数下传 / `useState` | **重新设计**，别照搬 |
| `useApi().request` / `useAsyncData` | Server Component + `lib/api` | 改写，守 server-only |
| 组件两端跑 | RSC + `"use client"` | 划分边界，交互叶子才 client |
| `$t` / `localePath` | `getTranslations`/`useTranslations` / `Link` | 换 API，语言包平移 |
| `useHead`/`usePageSeo` | `generateMetadata`/`buildMetadata` | 换实现，守 canonical/hreflang |
| `<style scoped>` | SCSS Modules | 换写法 |
| 自动导入 | 手动 import | 机械补全 |
| `pages:extend` + middleware | `[[...slugs]]` + 代码解析 | 重构路由 |
| xgplayer | hls.js（解密插件复用） | 重写播放器 |

## 结语

跨栈复刻，**难的从来不是语法翻译，而是心智模型的切换**：从"同构组件 + 全局 store + 声明式取数"，切到"服务端/客户端物理分层 + 服务端取数下传 + 渲染模式显式控制"。把这九个坑过一遍，两套 SSR 的差异就真正长在手上了。
